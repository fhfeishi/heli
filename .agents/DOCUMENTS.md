# 文档维护约定

本文规定信息归属、记录格式、更新时机、维护责任、清理条件和结构检查。规划方法见 [planning.md](rules/planning.md)，实现与代码审查见 [development.md](rules/development.md)，验证与完成判断见 [verification.md](rules/verification.md)，写作见 [writing.md](rules/writing.md)。

“信息放在哪里”表中的路径是模板默认载体。项目可以给 `.logsdev/` 下的文件改名，或让已有 Issue、PR、规格或工作记录承担同一职责；此时在“项目映射”登记，以登记位置为权威，默认文件随之删除，不维护平行副本。各规则中的 query、PROJECTION、INTERACTION、DECISIONS 均按登记映射解读。

## 术语与载体

- **query**：原始需求载体，保存用户原文与整理稿。
- **PROJECTION**：正式需求载体，保存总体目标、已确认要求和工作安排。
- **INTERACTION 或派发指定的任务记录**：当前工作载体。
- **DECISIONS**：决定载体。
- **设计载体**：状态为“现行”、已在“项目映射”登记的专题设计。
- 以上合称**权威载体**。其余过程材料是**工作文档**，不是权威载体。
- **有效要求**：当前明确指令、正式需求载体中未被取代的要求，以及现行决定和设计载体中的约束。
- **整理稿**：Agent 在 query 条目下写的整理和问题，不自动成为正式要求。
- **纳入版本控制**：不被 `.gitignore` 忽略、会被版本管理的路径，不要求已经提交。
- **被引用**：权威载体（含任务记录）用链接指向工作文档本身，目录型工作文档指向其目录内任一文件也算；写成路径加提交号的来源说明不是链接，不算被引用。

## 项目映射

<接入时登记改名或替代载体，每条写成 `名称 → 路径`，可一行多条（用“；”分隔），也可写成“| 载体 | 路径 |”两栏表格。名称只用 query、PROJECTION、INTERACTION、DECISIONS、删除记录、`设计载体（主题）`，例如 `PROJECTION → .logsdev/PROJECT.md`、`删除记录 → .logsdev/cleanup-log.md`、`设计载体（界面） → .logsdev/界面设计-20261019.md`。query、PROJECTION、INTERACTION、DECISIONS 或删除记录由 Issue 等外部系统承担时，路径写成完整链接；设计载体只能是 `.logsdev/` 下的本地文件或目录，是目录时写目录路径；本地路径一律用 `/` 分隔。未登记的按下表默认路径。>

## 信息放在哪里

| 信息 | 模板默认载体 | 边界 |
|---|---|---|
| 工程当前能力和使用方法 | 项目自己的 README、组件文档和接口契约 | 只描述当前实现和相应证据支持的事实 |
| Agent 通用原则和阅读路由 | `AGENTS.md` | 只放适用于所有任务的通用原则，行数上限见“词表与阈值”；必须纳入版本控制，机器相关内容不入库、也不另建第二份；具体方法链接到 `.agents/` |
| 反复使用的规划、开发、验证和写作方法 | `.agents/rules/` | 不记录项目进度和一次性结论 |
| 按需加载的 Agent skill | `.agents/skills/<名称>/SKILL.md` | 只放可复用的任务方法，不记录项目进度 |
| 规则、记录与模板的结构检查 | `.agents/verifier/check_rules.py` | 何时运行见 AGENTS；检查范围、基线与例外见本文 |
| 需持久保存的原始需求和整理稿 | `.logsdev/query.md` | 用户原文不改写；整理稿不自动成为正式要求；去向为已并入的条目移入 `query-archive/`，见“载体上限与出口” |
| 总体目标、已确认要求和工作安排 | `.logsdev/PROJECTION.md` | 面向未来，不记录执行流水；就地改写原条目，不按 query 或轮次追加小节 |
| 当前执行、依据、问题和下一步 | `.logsdev/INTERACTION.md` 或指定任务记录 | 只保留恢复和交接所需状态；就地改写，交接时整份改写为当前状态，不追加流水；任务结束（含中途放弃）时按“清理前保留什么”处理后恢复为模板 |
| 临时止血补丁的后续处理 | 当前工作载体的未决问题；结构性修正排入正式需求载体的工作安排 | 止血不是最终修法，必须有接收人 |
| 值得长期追溯的已确定决定 | `.logsdev/DECISIONS.md` | 只写决定、理由与代价、适用范围和必要的替代关系；按条目追加并维护开头索引；已作出的决定不改写，新决定取代旧决定（含撤销）时只在旧条目及其索引行注明取代关系；被取代的条目可移入 `DECISIONS-archive.md` |
| 删除了什么、为什么、原来在哪里 | 提交说明（尚未提交时写在交付说明）；项目在“项目映射”登记了删除记录的，同时写入 | 属于长期决定的另记决定载体；读者可能在原位置寻找时留一行注释说明去向；删除记录不是工作文档，不按工作文档清理 |
| 当前实现和验证覆盖 | 代码、schema、配置、测试、CI 或报告 | 文档引用可定位的结果，不复制机器可得事实 |
| 某主题的现行设计细节 | 状态为“现行”的专题设计，登记在“项目映射” | 由 PROJECTION 链接；采纳与取代见“状态表” |
| 调研、审查、方案草案、未采纳的专题设计和检查证据等过程材料 | 工作文档，见下文 | 不是权威载体；按“工作文档”清理 |
| 普通历史 | Git、PR 或已有任务系统 | 不按对话轮次另建归档 |

分析、候选方案和论证过程留在当前规划、讨论或工作文档中；决定形成后，不把完整思考过程搬入 DECISIONS。权威载体之间发生冲突时先识别信息类型（要求归正式需求载体，设计细节归设计载体，决定归决定载体），再核对有效要求、实现和验证证据，不能靠固定文件优先级掩盖差异。工作文档不参与这种裁决：它与权威载体不一致时只是待核对的线索。

规则只写在 `AGENTS.md` 与 `.agents/`，不写进 `.logsdev/`；记录目录不承担规则书的职责。信息类型增加时优先并入已有载体，并在上表登记；不为每类信息新建文件或目录——载体越多，每次改动要判断放在哪里、谁先失效的地方就越多。

## 记录格式

### 工作文档开头

第一个 `##` 小节之前（目录型写在其 `README.md`）每项一行，所有状态都写：

```
日期：2026-10-19
来源：用户指令 / query「某条目」 / 链接
状态：草案
```

日期是创建日期，写成真实的 YYYY-MM-DD，与文件名中的日期相同。状态词只用状态表第一栏，说明写在状态词后成对的括号里，例如 `状态：已废（被 界面设计-20261101.md 取代）`。

### DECISIONS 条目

条目标题为 `## D-YYYYMMDD-n 标题`，日期为真实日期，n 是当天序号，从 1 起。正文按需写，不必填满：

- 决定与范围；
- 理由与代价：为什么选它、放弃了什么、后续维护时容易误用的前提；
- 未采用：真实存在的替代方案及其代价，没有就不写；
- 依据：实际授权、需求或检查结果；尚未验证的写明；
- 替代关系：被取代时在正文末尾写“被 D-YYYYMMDD-n 取代”。

一句话能说清的决定就保持一句话，不倒造替代方案。

已作出的选择与理由不改写；条目里的实现位置、默认值和当前机制随代码更新，避免拿过期路径当依据。只取代一部分时写明被取代的范围，其余部分继续有效。

开头“## 索引”节每个条目一行：`- D-YYYYMMDD-n 标题｜适用范围或关键词｜现行`。被取代（含撤销）时末栏改为 `被 D-YYYYMMDD-n 取代`，并在旧条目正文末尾追加同样的一行，原内容不改；取代者须是编号更晚的条目（先比日期，再比当天序号）。编号重复时，后写的那条改用当天下一个空闲序号并同步索引，这不算改写决定。

### archive 清单

`.logsdev/archive/` 下每个顶层文件或目录，在 `archive/README.md` 的“## 清单”节占一行：`` - `名称` — 来源：…；删除条件：日期、事件或“无” ``。同一名称只登记一行；写“无”表示只作本地查阅，不再设删除期限。

## 状态表

| 状态 | 含义 | 处理时机 | 可转到 |
|---|---|---|---|
| 草案 | 待确认的方案 | 确认后改为现行；不再采用时改为已废 | 现行、已废 |
| 现行 | 当前有效的材料；经确认的专题设计此时是设计载体，须在“项目映射”登记并由 PROJECTION 链接 | 被取代或失效时改为已废 | 已废 |
| 已废 | 不再作为依据，括号写取代者或失效原因 | 不再被引用时可删除；被引用的保留 | 无 |

## 载体上限与出口

超过上限说明该载体需要收口，不是需要扩容。出口不补，收口就只能人工搬一次，下次照样长回来。

| 载体 | 上限（行） | 超限时的出口 |
|---|---|---|
| `AGENTS.md` | 100 | 把方法细节移到 `.agents/`，本文只留路由 |
| `query.md` | 400 | 去向为“已并入”且内容已在 PROJECTION 落地的条目，原文不改写地移入 `.logsdev/query-archive/<YYYY-MM>.md`；`query.md` 顶部保留“## 索引”，一行一条（日期｜一句话｜去向） |
| `PROJECTION.md` | 400 | 过期要求随节点快照移入 `.logsdev/archive/<日期>-节点/`，正文只留现行 |
| `INTERACTION.md` | 150 | 结束或交接时整份改写为当前状态；任务结束恢复模板 |
| `DECISIONS.md` | 600 | 被取代的条目移入 `.logsdev/DECISIONS-archive.md`，索引行保留“被 D-… 取代” |

## 何时更新

- 原始想法需要整理成熟时使用原始需求载体，模板默认是 query。用户当前明确指令已经足够时，可以直接工作，不为补流程而倒填记录。
- 总体目标、正式要求、完成条件或高层安排变化时更新正式需求载体，模板默认是 PROJECTION。
- 工作确需中断接续、交接或并行协调时更新当前工作载体，模板默认是 INTERACTION。
- 形成会长期影响架构、数据、公开接口、安全、兼容性或工作方式的确定决定时更新决定载体，模板默认是 DECISIONS；普通实现选择和调试过程不记录。
- 工程行为、接口或使用方式变化时更新相应工程说明，并以实际实现和检查为依据。

总体安排不复制任务明细。需独立接续的任务使用项目现有记录，或按 INTERACTION 模板另建任务记录并在派发时给出准确路径：放在 `.logsdev/` 下，命名为 `task-<主题>-<YYYYMMDD>.md`，与工作文档区分；总体安排只保留链接。任务结束后按“清理前保留什么”处理任务记录，再删除。

## 工作文档

调研报告、审查记录、方案草案、专题设计和检查证据等过程材料统称工作文档。工作文档可以作为参考和证据，但不作为需求或决定的来源；只写在工作文档里的建议不算已采纳。

- 专题设计经用户确认后成为设计载体：改为 `状态：现行`，在“项目映射”登记 `设计载体（主题） → 路径`，并由 PROJECTION 链接。设计载体只对该主题的设计细节有效，按权威载体维护：就地改写、不改文件名；同一主题只登记一份，被新设计整体取代时新设计另建文件，旧文件改为已废。
- 位置与命名：放在 `.logsdev/` 下，单文件命名为 `<主题>-<YYYYMMDD>.md`，日期为创建日期，同一天同主题有多份时加 `-HHMM`；有多个文件或附带截图、日志、来源时建同名目录，入口为 `README.md`。`.logsdev/` 不加分类子目录（如 reports/、tasks/），工作文档的同名目录和 `archive/` 不属于分类子目录；根目录不放散落的附件。需保存的检查证据放在产生它的工作文档或其目录中。权威载体引用的截图和附件放在纳入版本控制的路径，不放 `.logsdev/archive/`；放在工作文档目录中的，该工作文档被引用期间保留。
- 并入：用户确认的要求写入正式需求载体，确定的决定写入决定载体，并注明来源。来源已提交的，写路径和提交号（写成代码格式，不写成链接），这种引用不阻止删除；来源尚未提交或只在本地的，链接文档本身，被引用期间留在原处，提交后可改为路径加提交号再删除。来源被忽略、无法提交的，把并入所需的内容写进权威载体，不链接该来源，再按状态表处理它。这种链接只说明来源，不使它成为长期依据。
- 清理：不再被引用的已废文档可以删除，由使其不再被引用的人处理；删除前按“清理前保留什么”确认。仍需在本地查阅的可移入 `.logsdev/archive/` 并在清单登记。未被引用不构成删除要求，脚本对这种情况只给警告。
- `.logsdev/archive/` 只存放仍需在本地查阅的过时材料，内容不再改写，不作为依据或需求来源；未纳入版本控制的内容不能作为长期依据。

## 谁负责更新

- 用户确认产品目标、范围和完成条件；明确指令或已有授权足够时，不重复审批。
- 整理或规划工作的负责人维护项目约定的原始需求与正式需求载体。正式要求变化时，在受影响的任务记录中写明变化并通知当前负责人。
- 当前任务负责人维护项目约定的当前工作载体；接续者和集成者先核对采用的要求是否仍然有效。
- 多个 Agent 可能修改正式需求、决定或其他共享载体时，指定一名最终写入者；其他 Agent 提交结果、证据或建议，集成者依据集成后的事实更新记录。
- 人工审核集中于产品目标、完成条件、长期决定、静态协作制度和难以撤销的选择。授权范围内的执行状态、证据记录和常规同步由 Agent 直接维护。

## 清理前保留什么

覆盖或清理当前工作载体或工作文档前，确认已有可持久访问的位置保存：

- 可定位到具体版本的长期结论、实际检查结果及适用范围；
- 后续仍有效的要求、约束、未决问题和下一步：转入正式需求载体的“工作安排”；
- 记录所描述的代码或文件状态可以还原：已提交的写提交号；尚未提交的，在保留下来的记录或交付说明中写明工作区状态（改动了哪些文件），或保存可还原补丁。

未提交内容不能假设已由 Git 保存，也不因证据要求强制提交或建立归档。缺少持久依据时，保留当前记录并说明限制。

## 基线与例外

- 首次接入、已有记录无法一次清理时，运行 `check_rules.py --write-baseline` 初始化 `.agents/verifier/check_rules.baseline`（每行一条“C<检查> 文件 说明”，不含行号）。初始化只用于首次接入：基线文件在 git 历史中出现过时脚本拒绝初始化；基线文件不手工编辑，与最近提交的版本相比只减不增，多出的条目不生效并报失败（`--rebuild` 重建的基线提交后才成为比较对象）；删除后重新初始化须经用户批准，批准后加 `--rebuild`；基线文件无法读取时脚本报错且不写入。之后只有基线外的错误算失败。基线中有条目已消失时脚本报失败，再运行 `--write-baseline` 只删除已消失的条目，新增错误不会写入，基线只减不增。
- 单行例外写在出错的那一行末尾：`<!-- check-rules: 豁免 C<检查> 至 <YYYY-MM-DD> 由 用户 批准：<理由> -->`。“由 用户 批准”照写，只有用户本人批准后才能加；过期的例外无效。用户口头要求保留某项失败时，按 AGENTS 的交付写法说明，不写进基线。

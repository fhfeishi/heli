# 需求整理与规划

适用于整理想法、拆解工作；授权、状态和变更同步按 [DOCUMENTS](../DOCUMENTS.md)。

1. 先读用户原意，明确想解决的问题和预期结果。用户可以只写一句话，不要求先填完整模板。
2. 只补影响理解或执行的范围、限制和完成依据；区分用户要求、推断与建议，不编造指标、优先级或非目标。
3. 需要确认时给出整理稿和具体问题：需求来自原始需求载体的，写在对应条目下；否则在当前交互中提出。明确指令已有授权时直接推进。
4. 正式要求写入项目约定的正式需求载体，模板默认使用 PROJECTION，并保留确认来源。需求来自原始需求载体的，原条目按 DOCUMENTS 的“信息放在哪里”收口，不再维护一份相同需求。
5. 只细化足够行动的下一步。跨模块或并行工作补任务依赖和责任，探索任务随着新证据调整安排。

审核规划时，核对目标、步骤和完成依据能否对应；完成依据写明由哪项检查覆盖，证据类型按 [verification.md](verification.md) 选择；实现阶段新增测试也按其中的测试取舍。修订要求时处理受影响的任务与验收，接续和集成前核对要求是否已变化，具体规则见 DOCUMENTS。

## 方案选择

先从有效要求中提取判断标准、重要约束和当前未知，再形成方案，避免用第一个方案反向定义标准。

方案必须满足当前要求和约束；可行方案优先依据项目事实与证据，其次参考相近成熟产品，最后才依赖 Agent 推断。引用成熟设计时注明适用假设，并用最小实验验证影响选择的未知。产品目标、权限和成本取舍由用户决定。

当选择明显影响架构、兼容性、数据、安全、成本或其他难以撤销的事项，并且确实存在多个可行方向时：

1. 给出二至三个实质不同的方案；
2. 按相同标准比较收益、代价、适用条件和主要失败方式；
3. 推荐一个方案，并说明结论依赖的关键前提。

不要为数量制造虚假备选。局部修改、项目已有模式明确或只有一个合理方案时，说明依据后直接执行。

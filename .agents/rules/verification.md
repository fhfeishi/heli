# 验证

依据有效要求和实际改动取证，回答“凭什么说它完成了”。实现与代码审查见 [development.md](development.md)。

## 验证原则

验证服务于一个具体主张，不做没有主张的“跑一遍看看”。执行前先写明：要证明什么行为、什么结果算通过、什么结果能推翻它。

- 先列该改动可能的失败方式，再挑能区分它们的最小检查；需要新写测试时同样先列完失败方式再写。范围随风险扩大，不因为“更保险”而扩大。
- 开发期间，已有检查覆盖且相关输入未变的部分不重跑；收尾时执行全套。一次通过只支持它实际检查的那条路径，不外推到未检查的情形。
- 失败先分类：实现错、检查错，还是要求本身有问题。实现或检查错就改实现或检查；要求本身有问题时提请用户确认，不自行修改要求。
- 不靠重复运行获得通过：预期应通过的同一检查连续失败 2 次，即停止针对这项失败的修改尝试（测试驱动开发中计划内的首次失败不计入），报告失败分类和下一步，与之无关的已授权工作可以继续；不进入重试—修改—重试的循环，也不放宽断言。
- 输出以定位问题所需的最小信息为限，不打印大段无关上下文。

## 证据选择

每个完成声明都需要与风险相称的证据。按改动类型取默认证据；一次改动涉及多类时分别满足。

| 改动类型 | 默认证据 | 允许的例外 |
|---|---|---|
| 纯文档 | 链接、结构、事实和语义检查；不构造运行测试；规则与模板文档另按 AGENTS 运行检查脚本 | — |
| 调研或审查 | 来源可定位（链接、版本或日期），结论能回到来源；区分来源事实与推断 | — |
| 代码逻辑 | 至少构建或类型检查通过；行为变化并入覆盖它的最小端到端路径 | 项目没有构建或类型检查时，至少运行一次受影响入口；纯算法库等无法构造端到端路径时，用单元测试 |
| API、数据库、跨模块交互或外部服务 | 契约或集成测试；外部服务至少一次受控的真实验证或契约级验证 | 成本或环境不允许真实调用时用测试替身，并标明未覆盖范围 |
| UI 行为 | 构建通过后实际运行界面检查，附截图、录屏或改动前后对比图 | 环境无法运行界面时，完成构建和代码层检查，标明界面行为未覆盖，交用户验收 |
| 探索性原型 | 能回答目标问题的最小运行结果 | — |

采用例外时，在交付说明或任务记录中写明：默认证据为何不可行、实际用了什么检查、哪些行为仍未覆盖。

- 按待验证行为选择检查，先覆盖受影响部分，影响范围不明时再扩大。执行前核对配置、数据、外部写入和费用。
- 记录实际检查及其范围；未执行的检查明确标注。实现、检查和整体交付分别判断，只有约定完成条件满足时才声明相应范围完成。
- 要求变化后重查受影响部分；相关验证失效或检查受阻时，撤回已验证表述并记录影响。
- 并行改动以集成后的检查为准，单个分支通过不能替代集成验证。
- 结束时给出可复现成果：复现命令、输入、关键输出或产物位置。

## 测试取舍

测试是负债，只保留能区分真实失败的少数检查。测试类型按上表选择：行为变化默认端到端，接口和外部服务用契约或集成测试，单元测试只用于写明理由的例外。开发期间只运行与改动直接相关的单条。

新增测试须同时满足以下三条，任一不满足就不写：

1. 能说出它区分哪种真实失败，删掉它会漏掉什么缺陷；
2. 扩展已有用例无法覆盖这条路径；
3. 无法与其他简单测试合并。

禁止：

- 同义反复或自测试的测试，例如断言等于实现、Mock 复述被测步骤；
- 只检测实现是否变化的测试，例如锁定调用次数、顺序、内部字段；
- 代码写完后补写、且不属于上表例外的单元测试。

采用测试驱动开发时，先写会失败的测试再写实现，测试类型仍按上表选择，例如行为变化先写会失败的端到端用例；已通过的行为不追加测试。修缺陷时先构造一条修复前失败、修复后通过的复现检查作为修复证据，优先并入覆盖该行为的已有端到端用例；既不能并入、又不满足上面三条时，只作为本次的一次性证据运行并记录结果，不保留为测试。每个新增测试须在交付说明里写明它区分哪种失败、为何不能并入已有用例。

## 测试替身

先说明测试要回答的问题，再决定是否使用 Mock、Stub 或 Fake。

- 隔离本地逻辑、稳定模拟错误或控制时间时，可以使用测试替身。
- 验证真实接口、序列化、数据库、网络、文件系统或第三方兼容性时，不能只依赖替身；确实无法运行真实集成时按下一条处理。
- 不让 Mock 复制被测实现的内部步骤；调用次数和顺序只有属于公开约束时才断言。
- 因成本或环境限制无法运行真实集成时，按证据选择表的例外记录未覆盖范围，不把替身测试描述成集成通过。

## 反证检查

完成重要设计或实现后，检查：结论依赖哪些未验证前提，当前证据支持到哪里，当前需求和代码路径中真实存在什么主要失败方式，以及哪些内容尚未检查。

只报告有需求、代码或环境依据的风险，优先保留影响最大的少数问题；区分已经发现的缺陷与仍需验证的可能性。只有系统确实面对相应规模变化时，才推演扩容场景。

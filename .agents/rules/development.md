# 开发

依据当前明确指令、相关正式要求和代码开展工作。验证与取证见 [verification.md](verification.md)。需接续时读取派发指定的任务记录；文档归属与清理按 [DOCUMENTS](../DOCUMENTS.md)。

## 最小充分实现

- 先明确预期行为、边界和完成条件，核对相关接口、测试及有效决定。现有代码说明现状，不自动证明设计正确。
- 优先复用项目现有模式，只实现当前要求和验收需要的行为。没有当前用例支撑时，不新增扩展点、配置、抽象接口、通用框架或依赖。
- 项目现有代码和依赖不足以满足当前要求时，优先选用维护活跃、许可证合规的成熟库，不手写同类实现；组件库优先选源码进入项目、可直接修改的方式。同一职责（如 UI 组件、图标、动画、布局、拖拽、状态管理）项目内只用一个库，所选库自身依赖的底层库不算重复；界面的颜色、间距、圆角、字体等统一使用项目的设计 token 或主题，不混用视觉体系。尚无选型记录的职责，开始实现前确定所用库并经用户确认；新增同类库或替换已选库同样先说明理由并确认，用户已明确指定的除外。所选技术栈按 DOCUMENTS 记入决定载体，后续任务照此选用。使用 shadcn/ui（项目含 `components.json`）的 React 项目新增或替换 UI 组件、动画或页面块时，按 `.agents/skills/ui-component-sourcing/SKILL.md` 执行。
- 两处代码相似不足以证明需要抽象；只有共享语义稳定时才合并。范围外优化仅在具有明确后续价值时记录：有当前工作载体的记在其中，没有的写在交付说明；不顺手扩大改动。
- 保留他人修改，并行前明确写入范围和依赖。执行破坏性操作、外部副作用或产品范围变化前核对已有授权，超出授权或存在真实歧义时再确认。

## 迭代与替换

- 新旧逻辑互斥时按 AGENTS 整体替换。无调用方的旧代码连同过时注释、文档、配置一并删除，删除痕迹按 DOCUMENTS 的“信息放在哪里”留下。
- 删错再修是正常成本，不是保留旧代码的理由。删除影响对外契约、用户数据或兼容性时，按 DOCUMENTS 记录决定并显式确认。

## 原型与调查

争议来自技术可行性、接口行为、性能或工具限制时，用最小原型或调查回答一个写明的问题。争议来自产品目标、权限或成本接受程度时，原型不能代替用户决定。

得到答案后，明确选择丢弃、重写或纳入正式实现。一次原型成功只支持它实际检查的问题，不能据此宣称完整系统可用。

## 冲突与缺陷处理

- 实现中发现当前要求与既有上层接口、已确认设计或已有功能冲突时，停止自行取舍，指出冲突位置、可选方向和各自代价，确认后再继续。不默默绕过。裁决结论按 DOCUMENTS 同步到相应的正式需求、决定或设计载体。
- 缺陷定位到结构性原因时，提出结构性修正并说明影响面；不叠加条件分支、特例或兜底逻辑掩盖。补丁仅适用于边界清晰、修复局部、底层设计健康三者同时成立的小型问题；同一模块补丁叠补丁、修复牵动多处无关代码、需引入特判才能生效或会改变对外契约时，视为结构性原因。大小判定须定位根因后结合实际下结论，不得臆测。临时止血的小补丁需写明它不是最终修法，并按 DOCUMENTS 登记后续处理。

## 代码审查

先确认变更要解决的问题、有效要求和完成条件，再检查实现。影响较大或方案有争议时，在查看实现细节前先列出预期行为、关键不变量和可能方向；需要真实独立判断时，使用尚未读取差异的独立上下文。

审查重点是：

1. 是否解决原问题；
2. 是否引入行为回归、数据错误、安全问题或兼容性破坏；
3. 验证是否覆盖关键行为；
4. 是否存在当前要求不需要的抽象、依赖或复杂度，以及迭代后残留的死代码、兼容分支和已失效注释（说明删除去向的痕迹注释不算）；
5. 新增测试是否有同义反复、变化检测、可合并或本可并入已有用例的情况。

每项发现说明代码位置、触发条件、实际影响和最小修正，并区分确定缺陷、待验证风险和个人偏好。对于疑似过度设计，还需说明维护成本、删除后是否影响当前行为及如何验证。没有具体失败路径或工程影响的问题，不作为阻断项。

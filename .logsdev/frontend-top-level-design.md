# 第一部分 · 产品设计

## 1. 场景一：读懂资料

### 1.1 路径与页面状态

| 步骤 | 页面 | 关键状态 | 依赖的数据 |
|---|---|---|---|
| 1 进入库 | `/kb/$slug` | 章节树展开位置、文档分页、视图（列表/表格） | `tree`（sections + placements + documents） |
| 2 展开目录 | 同上 | 当前 `section` 及其子章节 | `sections`（parent_id、position） |
| 3 查找文档 | 同上 | 搜索词、范围提示（"当前章节及子章节 · N 篇"） | `documents`（分页 + 过滤） |
| 4 阅读章节 | `/kb/$slug/doc/$sourceId?chapter=&sha=` | 大纲、当前章节、原文窗口 | `outline` / `sections/<index>?sha256=` |
| 5 刷新恢复 | 同上 | 章节、滚动位置 | 路由 search params（§13.1） |

### 1.2 必须成立的行为

- **刷新后回到原处**：库、章节树展开态、文档、章节、滚动位置全部可恢复（这是路由 search params 承担 UI 状态的直接理由）。
- **搜索范围必须可见**：搜索框旁显示"当前章节及子章节 · 126 篇"，而不是把当前分页的 50 条当成范围；无结果时**不自动扩大到全库**，而是给出"扩大到全库"的明确动作。
- **索引不可用不阻断阅读**：目录与原文阅读独立于语义索引；索引状态单独披露（后端既有要求）。

### 1.3 验收（可定位）

打开某库某章节 → 复制 URL → 刷新 → 仍在同一章节同一位置；在无索引状态下仍可通读任意章节。

## 2. 对象与关系（本方案的语义底座）

### 2.1 四个容易混淆的概念

| 概念 | 含义 | 生命周期 |
|---|---|---|
| **任务** | 要解决什么问题（如"比较两条技术路线"） | 长期，可多次执行 |
| **会话** | 人与 Agent 讨论、调整任务的过程 | 可多轮，属于一个任务 |
| **执行记录** | Agent 某一次实际运行 | 一次性的、有状态与日志 |
| **模板** | 下次可复用的任务做法（含提示词 / Skill） | 长期，被任务引用 |

规则：同一任务可讨论多轮、执行多次，最后形成一份持续修订的成果。**不必每次追问都新建任务，也不必把每条回答都存成成果。**

### 2.2 资料侧的对象

| 对象 | 含义 | 备注 |
|---|---|---|
| 资料库 | 一批资料的集合，落盘为 `.knowledge/<slug>` | 沿用既有落盘约定 |
| 来源（source） | 一篇原始文档，稳定 `source_id` | 不可变快照由后端管理 |
| 章节（section） | 库内逻辑目录节点，稳定 `section_id` | 树形，可空 |
| 归属（placement） | 章节—来源关系，一来源可多处 | 移除归属 ≠ 删除来源 |
| 大纲 | 一篇原文内部的 ATX 章节结构 | 与库内目录**不是同一棵树** |
| 证据 | 原文中的字符区间 + 当时版本 | 复用后端 citations 的 `char_start/char_end` 与版本校验 |

### 2.3 三种「树」必须分开（操作动词不能共用）

| 树 | 用途 | 典型操作 | 禁止混用的说法 |
|---|---|---|---|
| **库分组** | 管理多个资料库 | 建库、改名、分层、镜像 | "移动""删除"指向库本体 |
| **库内目录** | 组织文档，同一文档可多处 | 归入章节、从本章节移除、章节改名/移动 | "删除"若指移除归属，必须说"从本章节移除" |
| **文档大纲** | 导航一篇原文内部章节 | 跳转章节、阅读 | 不存在"移动/删除"操作 |

**"从本章节移除"与"删除源文件"必须是两个不同的操作、两套确认文案。** 这与后端语义一致（移除归属不下线文档）。

### 2.4 提取侧的对象（详见 §5）

提取方案 / 提取运行 / 提取结果 / 证据 / 待复核项。

## 3. 导航与页面结构

### 3.1 一级导航：四个入口

| 入口 | 内容 |
|---|---|
| **资料库** | 资料组织、原文阅读、信息提取、检索 |
| **研究任务** | 最近会话、进行中的研究、历史执行记录 |
| **成果** | 笔记、报告、对比表等，可继续编辑 |
| **设置** | 模型、存储、能力配置 |

- 「新建研究」作为常驻主按钮，不占导航位。
- **任务模板**放在「新建研究」入口与研究任务页内；**提示词 / Skill** 放在模板的高级配置里，不设为一级功能。
- 与现状的差异：现有 `IconRail` 为 `chat / kb / tasks / artifacts / skils` 五项（`types.ts` 的 `NavKey`）。本方案把「对话」并入「研究任务」（会话是任务的一部分），并新增「设置」。

> **U1 已裁决（2026-09-28）**：采用四入口，**对话不保留独立一级入口**，并入「研究任务」。因此打开应用落在「研究任务」列表而非空对话——需相应处理现有默认首页（`nav="chat"`）的迁移与首次进入的引导。`skills` 退出一级导航，归入模板的高级配置。

### 3.2 库内三个入口

| 库内入口 | 主要内容 | 主要操作 |
|---|---|---|
| **资料** | 逻辑目录、文档列表、原文、大纲、来源说明 | 导入、归类、阅读、选择研究范围 |
| **信息提取** | 提取方案、结果表、证据、待复核项 | 创建方案、试提取、批量运行、核对 |
| **处理记录** | 导入、解析、检索索引、提取的执行情况 | 查看影响、重试、取消、检查失败原因 |

库的介绍、存储位置等移入库详情或设置，**不再设常驻栏目**。

### 3.3 页面清单

```
/knowledge                            库列表（多库浏览）
/knowledge/$slug                      库工作区：资料
  ?section=&q=&offset=&view=
/knowledge/$slug/doc/$sourceId        阅读页 ?chapter=&sha=
/knowledge/$slug/extract              信息提取：方案与结果
/knowledge/$slug/extract/$schemaId    单个提取方案：字段、运行、结果表
/knowledge/$slug/extract/$schemaId/runs/$runId   单次运行详情
/knowledge/$slug/jobs                 处理记录
/research                             研究任务：任务 / 会话 / 执行记录
/research/$taskId                     任务详情（含会话与执行记录）
/research/$taskId/runs/$runId         单次执行详情
/artifacts  ·  /artifacts/$id         成果（可编辑）
/settings                             模型、存储、能力
```

「知识台」三个字对应 `/knowledge` + `/research` + `/artifacts`；`/work`、`/life` 为工作台与生活台预留。

> **U1 已裁决（2026-09-28）**：`/knowledge` 等前缀**现在定下来**，不再留作待定，避免二次改名与深链失效。后续加台时按同一套前缀规则扩展。

## 4. 场景一的落地：资料库内部

### 4.1 三栏结构

```
目录树（章节） │ 文档列表（当前章节及子章节） │ 原文 / 大纲 / 来源说明
```

- 左栏是**库内目录**（`sections`），不是文件系统目录，也不是库分组。
- 中栏默认**列表或表格**，便于比较、筛选与批量操作。
- 右栏是阅读区；点击文档默认在右栏预览，双击或「展开阅读」进入 `/doc/$sourceId` 全页。

### 4.2 书架的位置（**U3 已裁决：降级**）

书架 / 卡片双视图解决的是「多个库怎么摆放」，而本轮核心是「进入一个库以后如何理解和使用资料」。因此：

- **库内文档与提取结果一律使用列表 / 表格**（可排序、筛选、批量、列比较）。
- **书架降级为「多库浏览」的可选视图**，不作为强制资产，**不进入本轮验收路径**（`/knowledge` 库列表页可保留其作为视图切换项，但不为其投入新工作量）。

实施口径：先让 S1 的列表/表格路径完整可用，书架作为既有资产保留；只有当多库数量增长到列表不再够用时，再评估是否继续投入。降级不等于删除代码——`ShelfView.tsx`、`KbCard.tsx` 保留，但不作为验收对象、不优先修缺陷。

### 4.3 搜索与范围

- 搜索框旁**必须显示范围**：`当前章节及子章节 · 126 篇`。
- 无结果时给出「扩大到全库」按钮，**不静默扩大**。
- 检索结果项显示命中段落与所在文档，点击定位到原文字符位置（§6.3）。

### 4.4 处理记录

导入、解析、索引构建、提取四类任务的执行情况集中在此；状态机与交互规则见 §7。库级「锁忙」在此给出可执行的下一步（重试 / 稍后 / 查看占用者）。

## 5. 场景二：加工资料 —— 信息提取（本版重点展开）

面向用户的名字是**「信息提取」**，对应 query.md 提出的 `target/` 与 `target-schema.json` 构想。

### 5.1 三个对象

| 对象 | 内容 |
|---|---|
| **提取方案** | 目的、字段定义、提取指令、缺失信息的处理方式 |
| **提取运行** | 选中的资料范围、输入版本、方案版本、进度与失败项 |
| **提取结果** | 字段值、原文证据、复核状态、人工修订 |

同一批资料可套用多个方案（例如「技术应用分析」与「项目申报依据」），**无需复制原文**。

### 5.2 交互流程

```
定义字段 → 选择几篇试提取 → 对照原文调整 → 批量执行 → 筛选结果 → 进入研究
```

界面提供**字段表单**（名称、类型、说明、是否必填、缺失时如何表示）+ 高级编辑入口（直接编辑 schema / 提示词）。**不要求用户先手写 `target-schema.json`**——底层字段定义与提示词同属一个提取方案，表单与高级编辑是同一份数据的两种编辑方式。

### 5.3 结果与证据

| 规则 | 说明 |
|---|---|
| 缺失 ≠ 失败 | 原文没有的信息显示**「未提及」**，提取失败显示**「失败」**，两者不得合并为一个空白 |
| 证据可点开 | 有事实含义的字段能点开**对应证据片段**（字符区间），不只是跳到文档首页 |
| 回到原文 | 提取结果是查找与比较的辅助材料，最终论证仍能回到原文 |

证据指针复用后端既有机制：`citations` 已保存 `char_start/char_end` 并在保存时校验分片属于该来源的当前版本。

### 5.4 记录粒度：一条记录代表什么（本文补充）

一篇论文可能包含多个实验或技术应用，**不能默认「一篇文档一行」**。提取方案必须声明记录粒度：

| `record_scope` | 一条记录代表 | 定位字段 |
|---|---|---|
| `document` | 整篇文档 | `source_id` |
| `segment` | 文档内某个章节 / 实验 | `source_id` + 章节或字符区间 |
| `entity` | 文档内某个技术 / 方法实体 | `source_id` + 字符区间 |

结果表首列必须显示「本行代表什么」，避免用户把实体级结果误当作文档级结论。

### 5.5 过期与覆盖（本文补充：复用后端版本机制）

| 场景 | 行为 |
|---|---|
| 原文更新 | 结果标记**「待更新」**，不静默替换 |
| 方案更新 | 受影响字段标记「待更新」 |
| 人工修订 | **人工修改不被下一次自动提取覆盖**；重新运行后可查看差异再决定采纳 |

判定依据不需要新机制：后端已有不可变版本 `version_id`（覆盖原文哈希、解析身份与分块配置），提取结果同时记录 `source version_id` + `schema version`，任一变化即标记过期。

### 5.6 与后端的关系

- 提取方案落盘位置建议沿用 query.md 的 `target/`（与 `source / parsed / vectordb / datadb` 同级），**具体命名以既有落盘决定为准**，本文不新增目录约定。
- 提取结果属于**可重建但昂贵**的产物：方案与范围可复现，因此不必进入 P0 备份，但需可重跑。
- 依赖确认：后端当前**没有** target/提取能力，S2 场景需要后端配合（**U4 之前无法启动 S2**）。

### 5.7 验收（可定位）

建一个含「应用场景 / 问题 / 技术方法 / 成果指标 / 作者 / 时间」的方案 → 选 3 篇试运行 → 至少 1 个字段点开证据并定位到字符区间 → 批量跑 → 修改其中一篇原文后该行显示「待更新」→ 人工改一个字段再重跑，人工值不被覆盖且可看差异。

## 6. 检索路径与范围

### 6.1 正面处理 BM25 与既有向量选型的冲突（**U2 已裁决**）

冲突事实（三份材料不一致）：

| 来源 | 主张 |
|---|---|
| `query.md`（2026-0928） | 「现阶段我们不考虑任何重型 RAG，bm25 就好」 |
| `.knowledge/README.md` §6 / §8 | 目标配置为 BGE-M3 dense（1024 维）+ Chroma cosine；真实库 `active` 索引文档 0、向量文件 0 |
| 副本实测（交付报告） | BGE-M3 全量 60,267 向量、1,423 来源、耗时 1,349.3 秒 |

**补充一条证据，避免误判成本**：BM25 目前同样**没有实现**。`.knowledge/README.md` §9 明确「中文短词和代码标识符不能假设默认 FTS5 已覆盖」，即 FTS5 尚未落地。所以这不是"换一个现成方案"，
而是**两条路都还有后端工作量**——向量是"未在真实库发布"，BM25 是"未实现"。

**本文对前端的处理（不依赖裁决结果）**：本轮知识台以**目录浏览、原文阅读、全文检索**为基础交付；语义/向量检索是**可选增强**，不作为前端交付前提。已有数据与实现保留。

> **U2 已裁决（2026-09-28）**：本轮范围为**目录 + 原文 + 全文检索（BM25 优先）**，向量检索保留为可选增强、单独排期，**不阻塞前端交付**。同时按上述证据明确记录一处范围调整：`.knowledge/README.md` §6/§8 的 BGE-M3 + Chroma 是**目标配置**，不是本轮需求；「现阶段 bm25 就好」也不是"换一个已实现的方案"，**BM25/FTS5 与向量发布都仍需后端工作量**。前端只按 §6.2 的通道契约对接，两者都不改前端设计。

### 6.2 检索通道抽象（本文补充）

前端只依赖一个通道契约，不关心后端用什么引擎：

```
输入：scope（库 / 章节及子章节 / 选定来源集合） + query + 分页
输出：hits[] { source_id, 标题, 命中片段, char_start/char_end, 分数, 版本标识 }
```

BM25、向量、混合检索都是这个契约的实现。因此 **U2 无论怎么裁，前端设计不变**。

### 6.3 三种使用方式的优先路径

| 问题 | 优先路径 |
|---|---|
| 「打开持久化章节」 | 目录 → 指定章节 → 原文 |
| 「这些资料哪里提到检查点？」 | 范围内全文检索 → 命中段落 → 原文 |
| 「哪些技术适用于这个场景？」 | 提取结果筛选 → 候选资料 → 原文核对 |

**提取摘要可能遗漏信息**，所以提取结果页必须保留「继续搜索原文」的入口，不能让用户以为结果表就是全部。

### 6.4 范围与失败提示

- 范围可见（§4.3）；无结果不静默扩大。
- 检索失败时区分：范围为空 / 索引未就绪 / 后端锁忙 / 引擎错误——各自给出可执行的下一步。

## 7. 执行期间（Agent 工作台）

### 7.1 用户可见的执行状态

```
排队 → 执行中 → 等待用户补充 → 已完成 / 失败 / 已取消
```

不要求引入流程引擎，只要求用户能判断四件事：**正在做什么 / 已完成什么 / 为什么停住 / 接下来能做什么**。

### 7.2 执行所有权归后端（回答 v1 §5.4 未解决的问题）

v1 把"生成中的内容放组件局部、结束后写缓存"只解决了渲染开销，没有回答页面卸载、连接中断、返回任务怎么办。本版明确：

- **执行状态是后端事实**，落在既有 `jobs` 表；前端是**观察者**。
- 页面切换 = 卸载订阅，**不等于取消任务**；返回时按 `runId` 重新订阅，拿到实际进度与已产生内容。
- 断连 = 重新订阅 + 补齐缺失事件（按事件序号或游标），而不是从头重放。
- 渲染仍在组件局部做增量批处理（v1 §5.4 的写法保留）——**降低渲染开销**与**保持执行连续性**是两件事，分别解决。

### 7.3 规则清单

| 规则 | 说明 |
|---|---|
| 切换页面不取消 | 见 §7.2 |
| 「停止」有两种语义 | 「取消请求已发出」与「后端确认已停止」必须在界面上区分，不能点了就当停了 |
| 部分失败保留结果 | 明确列出哪些资料未处理及原因 |
| 不悄悄改变已开始的运行 | 修改资料范围或模板只影响**下一次**运行 |
| 展示可核对的工作过程 | 检索了什么、读了哪些章节、调用是否成功、生成了什么 |
| 开销信息进详情 | Token、首字延迟、耗时放运行详情；主界面优先呈现任务进度与结果 |

> **U7 已裁决（2026-09-28）**：「停止」必须走**后端真实取消**（省 token），界面区分「已发出」与「已确认」，不得点了就算停。

**工作过程不是模型内部思维的完整记录**。展示口径是"可核对的动作与产物"，避免把推测包装成事实。

## 8. 右侧面板

### 8.1 先定义行为

| 操作 | 预期行为 |
|---|---|
| 点击答案中的引用 | 右侧打开原文并定位证据，保留中间对话 |
| 点击提取结果的字段 | 右侧显示对应原文片段 |
| 打开成果 | 查看或编辑，并明确保存状态 |
| 固定右侧内容 | 后续点击不自动覆盖，提供明确的替换动作 |
| 展开阅读 | 进入主区域，返回时恢复原任务的位置 |
| 关闭面板 | 保留主区域的输入、选择和滚动位置 |

> **U8 已裁决（2026-09-28）**：成果采用**显式保存**。补充规则：**成果处于未保存编辑状态时，点击引用不能直接替换它**——先提示保存或放弃，不静默替换。

### 8.2 布局待定（修正 v1 的错误）

v1 写「Inspector 仍是浮层，观感不变」**与代码不符**：`heli-web/src/App.tsx` 中 `Inspector` 是 `<main>` 的**并排兄弟节点**，且 `nav === "kb"` 时**根本不渲染**公共 Inspector。

因此目标布局按模块区分（**U6 已裁决 2026-09-28**）：

| 模块 | 布局 | 理由 |
|---|---|---|
| 资料库 | **并排常驻** | 目录 + 列表 + 原文 + 证据需要同时可见 |
| 对话 / 研究任务 | **浮层** | 注意力应落在问题与回答上，中间产物按需查看 |
| 窄屏 | 允许切换主视图 | 避免同时挤入导航、目录、列表、正文和面板 |

实施含义：`App.tsx` 现有「`nav === "kb"` 不渲染公共 Inspector」是**与裁决相反**的现状——知识库恰恰是最需要并排面板的模块。改造时以本表为准，`?panel=` 的状态表达（§8.3）服务于这个布局，不是替代它。

### 8.3 状态保存方式

行为定下来之后，才谈状态放哪：面板开关与内容用路由 search params 表达（`?panel=`），以获得刷新恢复与深链；**这不替代 §8.1 的行为定义**。

## 11. 数据流与状态管理

### 11.1 三分法

| 类别 | 内容 | 归属 |
|---|---|---|
| Server State | 库/章节/文档/来源/提取方案/结果/执行记录/会话/成果 | TanStack Query（真源在后端） |
| Client UI State | 视图偏好、选中集、本地组织视图、面板固定、Toast | Zustand 切片 |
| Ephemeral | 流式增量、拖拽中间态、输入框草稿 | 组件内 `useRef`/`useState`，不进全局 |

**执行状态不在任何一栏**——它是后端事实，前端只订阅（§7.2）。

### 11.2 能被后端回答的状态一律不进 Zustand

这条直接消掉 P9（"点了说落盘其实没落盘"）。

### 11.3 撤销要分清两层（修订 v1）

v1 把"整树快照撤销"作为选状态方案的依据。修正为：

| 层 | 对象 | 机制 |
|---|---|---|
| **本地视图撤销** | 书架分组、顺序、镜像 | 整树快照（`groups` + `ungroupedOrder` + `mirrors` 一起压栈/恢复），规模是 ID 级，代价可忽略 |
| **已保存数据撤销** | 章节归属、提取方案、成果 | **不能靠前端快照**；必须走后端操作或显式逆操作 |

**旧快照不能覆盖外部更新**：本地视图撤销恢复的是"视图"，不是"数据"；若期间后端数据已变，恢复结果以服务端当前事实为准并提示差异。

### 11.4 持久化

| 数据 | 方式 |
|---|---|
| 领域数据 | 后端权威，前端不持久化 |
| UI 偏好 | `persist` → localStorage |
| 组织视图 | **落盘**（U5 已裁决）：作为独立于 `sections` 的视图数据由后端存储；后端提供前 persist 到 localStorage **并标注「本地仅」**，不冒充已保存 |

## 12. 组件与样式

### 12.1 Tailwind v4 token 三层

L1 原始值 → L2 语义（组件只许用这层：`bg-canvas`、`text-micro`、`rounded-card`）→ L3 组件级复合。保留 `--spacing: 1px`（数字即像素）与 `@theme static`。新增 `reduced-motion` 全局降级。

### 12.2 与 shadcn/ui 的关系

| 维度 | 结论 |
|---|---|
| copy-in 形态 | 一致（组件源码归我们），无需改变 |
| 行为底座 | **引入 Radix**，替换手写 Dialog/Popover/Menu/Tooltip（现有 KB-07/KB-09 缺陷） |
| token 命名 | 渐进对齐，旧 token 保留别名，不一次性改名 |
| 间距体系 | **不迁移**（rem vs 1px）。因此**从 shadcn/Radix 示例复制的类名串必须重写尺寸类**，直接粘贴会缩小约 4 倍 |
| `cn()`（clsx + tailwind-merge） | 引入，纯收益 |
| 图标 | 引入 lucide-react，领域图标保留自绘 |

### 12.3 组件三层与状态齐套

Primitive（Radix 封装）/ UI 基础件（无 store、无请求、无领域名词）/ Feature 组件。

每个可交互组件定义 5 态（`default / hover / focus-visible / disabled / loading`），每个列表视图定义 `empty / error / loading`。**error 与 empty 是现状缺失最多的**，而后端恰好会返回「锁忙」「索引未就绪」「版本过期」三类必须可见的错误态。

## 13. 路由、接口与类型

### 13.1 路由：TanStack Router

选型理由是**支撑 S1**：typed search params 让"库 + 章节 + 文档 + 章节序号 + sha"成为可寻址、可刷新恢复、可深链的定位串，而不是内存里的一堆 state。

UI 状态真源（`?view=` `?section=` `?q=` `?chapter=&sha=` `?panel=`）；瞬态（拖拽、hover、草稿）留在内存。

### 13.2 传输

| 通道 | 用途 |
|---|---|
| REST over `fetch`（`/api`，Vite 代理 8765；Tauri 下改直连或 command） | CRUD |
| SSE | 流式回答、执行事件 |

不引入 WebSocket：单向即可，SSE 走 HTTP、自带重连、Tauri 无需额外配置；中断用 `AbortController` + 关闭流。

### 13.3 类型：只在真实转换的边界分层（修订 v1）

v1 写"所有对象统一套 DTO / VM / mapper"，会造成机械复制类型。收窄为：

| 边界 | 是否分层 |
|---|---|
| kb / document / section / source / extract / run（**后端有真实契约**） | 是：DTO + VM + mapper |
| 纯前端 UI 对象（视图偏好、面板状态、Toast） | 否：直接定义，不造 mapper |

契约来源：优先后端导出 OpenAPI 生成；后端暂不提供时，用手写 zod schema 固定（且 zod 可复用于路由 search params 与表单校验）。

### 13.4 统一错误模型

```ts
type ApiErrorCode =
  | "NETWORK" | "LOCK_BUSY" | "VERSION_CONFLICT" | "INDEX_UNAVAILABLE"
  | "NOT_FOUND" | "CONFLICT" | "VALIDATION" | "UNKNOWN";
```

每种 code 有固定的、带"下一步"的呈现：`LOCK_BUSY` → 稍后重试 + 占用说明；`INDEX_UNAVAILABLE` → 检索不可用但目录与原文可读；`VERSION_CONFLICT` → 新旧页不能混读。对应 `.knowledge/README.md` §9 的硬要求。

### 13.5 Mock

MSW 取代 `data/mock.ts` 与 `notReady()` 双轨——但**按场景需要引入，不作为前置阶段**；S1 只 mock 已存在的目录/文档/章节接口。

## 14. 第三方库选型（实现者自行决定，不再提交用户裁决）

### 14.1 总表

| 关注点 | 选型 | 被否方案与理由 |

## 15. 性能：先测瓶颈，不预设手段

修订 v1：v1 广泛要求虚拟化、Worker、固定性能指标。改为：

| 做法 | 调整 |
|---|---|
| 预设虚拟化 / Worker | 先测实际瓶颈；确需时再引入，并说明是针对哪个操作 |
| 固定性能预算数字 | 注明**设备、数据规模、操作条件**（如"WSL + 1,423 文档 + 滚动"），否则数字不可验收 |
| 已知的重活 | 仅两条现在就成立：导出自包含 HTML 同步构建会卡主线程（移入 Worker）；1,423 条文档列表应先分页（后端已分页，前端不一次性取全量） |

流式渲染仍按 §7.2 在组件局部做 rAF 批处理——这是**渲染**问题，与执行连续性分开。

## 16. 实施：每个场景交付一条完整用户路径

### 16.1 S0 · 最小必要地基（不占阶段，随 S1 一起做）

只做三件支撑"真实反馈"的事：

1. `.gitignore` 的 `lib/` 锚定为 `/lib/`（一行）。
2. 统一 `api/client.ts` + `errors.ts`，所有写操作走同一出口并给出真实成败。
3. 消除 P9：未接后端的入口要么有完整行为（mock），要么不出现，不允许"点了说成功其实没做"。

**不做**：全量 lint/测试基建、目录大搬移、状态库替换。

### 16.2 三个场景

| 阶段 | 场景 | 完成的路径 | 只做支撑它的改动 | 验收（可定位） |
|---|---|---|---|---|
| **S1** | 读懂资料 | 进入库 → 展开目录 → 查找文档 → 阅读章节 → **刷新后恢复位置** | 接入路由与 search params；`kb-read` 走 Query；章节窗口缓存 | 复制 URL → 刷新 → 回到同一章节同一位置；无索引状态下仍可通读 |
| **S2** | 加工资料 | 创建提取方案 → 小批试运行 → 核对证据 → 批量提取 → **原文更新后标记过期** | 新增 `features/extract`、`entities/extract`；结果表 + 证据定位 + 双版本比对 | 见 §5.7 |
| **S3** | 完成研究 | 选择资料 → 发起任务 → 查看执行过程 → 打开引用 → 编辑成果 → **返回后继续** | 新增 `features/run`（订阅后端执行状态）；面板行为 §8.1；成果编辑与保存状态 | 发起 → 切页 → 返回仍见实际进度；停止区分「已发出/已确认」；引用点击定位证据且不丢对话 |

### 16.3 依赖与顺序

- **S1 无后端新依赖，现在就做**（本轮首个交付）。
- **S2（U4 已裁决）**：前置条件是后端提供一版 `target-schema.json` 样例 + 提取接口。在此之前前端只做**契约（zod/端点定义）+ MSW mock + 界面骨架**，并明确标注为未接后端；**接上真实提取接口后才计入 S2 验收**，不得以 mock 通过宣称完成。
- **S3** 依赖后端 jobs/执行接口；会话与成果存储按 U5（组织视图落盘，未提供前标「本地仅」）与 U8（显式保存）执行。

### 16.4 测试取舍（按项目验证规则）

优先覆盖**少数真实端到端失败路径**，不为覆盖率补 smoke：

| 检查 | 区分哪种失败 |
|---|---|
| 刷新恢复定位（Playwright） | 路由状态丢失 / 章节窗口错位 |
| 库改名或改归属 → 重启 → 刷新保持 | 前端假装成功（P9）/ 契约漂移 |
| 提取结果在原文更新后标记过期、人工修订不被覆盖 | 静默替换 / 覆盖用户编辑 |
| 执行中切页返回仍见进度 | 前端持有执行状态导致任务被取消 |

## 17. 裁决结果与实施边界

### 17.1 已裁决（2026-09-28，按本文倾向确定；已回写 [DECISIONS](DECISIONS.md)）

| # | 问题 | 影响 | 裁决结果 |
|---|---|---|---|
| **U1** | 一级导航与对话入口；`/knowledge` 前缀是否现在定 | 信息架构与路由顶层 | **四入口**：资料库 / 研究任务 / 成果 / 设置。**对话不占一级入口**，并入研究任务（默认首页改为研究任务列表，需处理现有 `nav="chat"` 迁移）；`skills` 归入模板高级配置。**前缀现在定**，后续加台沿用同一规则 |
| **U2** | 检索通道本轮范围 | 后端工作量与交付范围 | **本轮 = 目录 + 原文 + 全文检索（BM25 优先）**；向量检索为可选增强、单独排期、不阻塞前端。同时记录范围调整：BGE-M3 + Chroma 是目标配置而非本轮需求，且 **BM25/FTS5 同样未实现**，两条路都仍需后端做工 |
| **U3** | 书架是否降级 | §4.2 与 v2 视觉资产去留 | **降级为「多库浏览」的可选视图**；库内一律列表/表格；不进本轮验收路径，代码保留但不优先投入 |
| **U4** | 后端何时提供 target / 提取能力 | **S2 前置依赖** | 需先有一版 **`target-schema.json` 样例 + 提取接口**。此前前端只做契约 + MSW mock + 界面骨架并标注未接后端；**接上真实接口后才计入 S2 验收** |
| **U5** | 组织视图（分组/顺序/镜像）是否落盘 | Server State 还是 localStorage | **落盘**：作为独立于 `sections` 的视图数据由后端存储；后端提供前存 localStorage **并标注「本地仅」** |
| **U6** | 右侧面板布局 | §8.2 | **按模块区分**：资料库并排常驻、对话/研究任务浮层、窄屏允许切换主视图 |
| **U7** | 「停止生成」是否需要后端真实取消 | 取消语义与 token 开销 | **需要真实取消**；界面区分「已发出」与「已确认」，不得点了就算停 |
| **U8** | 成果保存模型 | §8.1 的保护规则 | **显式保存**；未保存时点击引用先提示保存 / 放弃，不静默替换 |
| **U9** | 提取记录的默认粒度 | 结果表首列语义 | **方案显式声明 `record_scope`，默认 `document`**，允许 `segment` / `entity`；结果表首列必须显示「本行代表什么」 |

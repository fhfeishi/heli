# 资料库背景系统与 LLM 辅助模块设计（候选方案）

> 状态：**候选，未批准**。用户 2026-10-18 提出：将 heli 构建为专业的资料管理底座——资料库分组、每组/每库的「背景」、系统预设背景模板（科研项目-横向 / 纵向 / 其他）、用户自定义背景的渐进完善、不强制边界清晰但系统要给出提醒与优化建议（做成 LLM+prompting 模块、模块化），覆盖个人积累 / 笔记 / 手稿 / 科研论文 / 技术博客 / 源码解析等类型，整体结合 AI Agent harness rules。
> 本文是 [library-system-design.md](library-system-design.md)（分组、分面、视图——管「怎么摆」）的姊妹篇：本文管「每个库/组是什么、边界清不清、AI 怎么帮忙」。批准前不启动实施；批准后写入 [DECISIONS](DECISIONS.md) 并转为实施规格。

## 1. 要解决什么

库会越来越多：现有 12 个，Bot-Reports 待接入，之后还有个人积累、论文、博客、源码解析。三个真实问题：

1. **「这个库是干什么的」只有一句话 `description`**——新建时随手写的一句，之后没人补，半年后自己也想不起来边界在哪。
2. **用户不想要强制分类**（每次建库填一张表太重），但**想要系统在边界模糊时提醒**——"这两个库背景重叠了"、"这份资料好像两个库都能放"。
3. **agent 需要读懂库的定位**才能正确入库、检索、引用——背景是给人和 agent 双读的契约，这是「结合 AI Agent harness rules」的落点。

## 2. 核心概念：背景（background）

背景 = 一个库/组的**自述**：为什么存在、收什么、不收什么、资料从哪来、打算怎么用。

两级，职责不同：

| 级 | 背景回答 | 落盘建议 |
|---|---|---|
| 资料库组 | 这个组为什么存在、组内各库怎么分工 | `_layout.json` 的 `groups[].background`（短叙述字段） |
| 资料库 | 来源、覆盖范围、时间跨度、用途、边界声明 | 库根 `background.md`（叙述）+ `kb.json.background`（结构化字段：模板 id、边界关键词） |

落盘形态的理由：

- **`description` 保持一句话不变**（现有 12 个库不动）；背景是新增层，不是替换。
- **叙述部分用 md 不用 JSON 字段**：背景是长文本，要给人读也要给 agent 读，md 天然合适；且符合「目录即权威」——`background.md` 就在库里，随库整体备份迁移。
- **结构化字段进 `kb.json`**：模板 id、边界关键词这类要被程序消费的（边界检查、UI 徽章）放 JSON，避免解析自由文本。

## 3. 背景模板（系统预设）

模板 = **引导字段清单 + 填写示例**，不是强制校验。预设一批，用户可自定义：

| 模板 id | 适用 | 引导字段（示例） |
|---|---|---|
| `project-hengxiang` 科研项目-横向 | 企业/事业委托、四技合同、产学研 | 委托方、合同号、经费与节点、交付物、保密要求 |
| `project-zongxiang` 科研项目-纵向 | 基金委/部委/省市立项 | 批准号、负责人、起止年限、任务书与验收口径 |
| `project-other` 科研项目-其他 | 自筹、校内、国际合作等横纵都不完全归类的 | 资金来源、立项主体、验收方式 |
| `personal` 个人积累 | 笔记、手稿、学习记录 | 主题、形式（笔记/手稿/摘抄）、时间跨度 |
| `papers` 科研论文 | 论文集合 | 领域、来源（会议/期刊/arXiv）、更新方式 |
| `tech-blog` 技术博客 | 博文、教程 | 主题、来源站点、抓取时间 |
| `source-analysis` 源码解析 | 开源项目源码/文档镜像 | 上游项目、版本、镜像时间、阅读重点 |
| `custom` 自定义 | 以上都不适用 | 自由字段 |

要点：**模板只是脚手架**。选模板 = 拿到一份引导字段，填多少随意（见 §4）。模板本身也是文件（`prompts/templates/*.md`），可版本化、可 diff、可随实际使用修订。

## 4. 渐进式背景：不强制边界清晰

明确接受用户原则：**不强制每个库/组边界清晰**。对应设计：

| 完整度级别 | 含义 | 系统行为 |
|---|---|---|
| L0 空 | 只有库名 | 正常可用；UI 显示「背景待补」徽章（不阻塞任何操作） |
| L1 一句话 | 新建时的简短说明（现状） | 正常可用；LLM 模块可主动提议补全（§5） |
| L2 模板字段 | 按模板填了关键字段 | 边界检查可用 |
| L3 有边界声明 | 明确写了「收什么 / 不收什么」 | 边界检查最可靠；agent 自动入库可按声明执行 |

- 任何级别**不阻塞**上传、检索、移动等操作；完整度只是提示。
- 「边界不清晰」不是错误，是一个**可被系统发现和讨论的状态**——这正是 LLM 模块的存在意义。

## 5. LLM+prompting 模块（模块化设计）

### 5.1 位置与边界

新模块 `heli-src/agent/background/`（现状 `agent/` 下只有一个 `config.py`，无冲突）：

```text
heli-src/agent/background/
├── prompts/                # prompt 模板文件（.md，版本化，可 diff）
│   ├── complete.md            # 背景补全
│   ├── boundary-check.md      # 边界检查
│   └── suggest-group.md       # 归组建议
├── templates/              # 背景模板包（§3）
├── service.py              # 编排：收集上下文 → 调 LLM → 产出结构化建议
└── README.md               # 模块契约
```

与检索、摄取（kbctl/pipeline）**完全解耦**：模块只读库元数据（kb.json、tags、抽样标题），只产出**建议对象**，永不直接写库。

### 5.2 四个能力

| 能力 | 输入 | 输出 | 触发 |
|---|---|---|---|
| **背景补全** | 一句话说明 + 模板字段 + 抽样资料标题 | 草拟的完整背景（md diff） | 用户点「补全」/ 新建库后提示一次 |
| **边界检查** | 全库/组的背景 + tags + 抽样标题 | 重叠对清单 + 每个重叠的澄清建议 | 手动 / 新建或移动库时 |
| **归组建议** | 新库背景 + 现有组背景 | 建议进哪个组（含「都不合适，建议新建组」） | 新库登记后 |
| **模板修订建议**（低频） | 各库实际填写的字段使用情况 | 模板字段的增删建议 | 手动 |

### 5.3 工程原则（harness rules 的落法）

1. **建议-确认-执行三段式**：LLM 产出永远是「建议对象」（JSON：类型、目标库/组、diff、理由），UI 呈现，用户确认后才落盘。模型不持有写权限。
2. **prompt 即文件**：所有 prompt 是 `prompts/*.md`，进版本库，可评审、可回滚。few-shot 示例从真实库背景里挑。
3. **可整体关闭**：无 LLM 凭据或用户关闭时，模块静默退出，其余功能（分组、检索、背景手填）不受影响。背景系统不依赖 LLM 才能用。
4. **背景即 agent 上下文**：agent 对库做任何操作（入库、检索、引用）前，先读该库 `background.md`——这就是「结合 AI Agent harness rules」的具体形式：每个库自带一份「对本库能做什么、不能做什么」的声明，agent 的行为边界由资料自己声明，而不是写死在 agent 代码里。
5. **成本与延迟**：边界检查是全库两两比较，库数增长后按「背景哈希变了才重查」做增量；单次调用限定抽样规模（如每库 20 个标题），避免大库扫爆 token。

### 5.4 幻觉防线

- 背景补全的草稿里**不允许出现资料里没有的事实**（如编造合同号）——prompt 里硬性约束「不知道就留空并标注待填」。
- 边界检查的「重叠」结论必须附上**双方背景原文片段**作为证据，不允许只给结论。

## 6. 与既有设计与裁决的关系

- **分组与分面** → 姊妹篇 [library-system-design.md](library-system-design.md)（同为候选）：那篇的组字段会扩展 `background`；两篇批准与否互相独立，但实施时 P 期要合并排序。
- **U5（组织视图落盘）**：组背景进 `_layout.json` 是其自然延伸，不冲突。
- **`kb.json` schema**：新增 `background` 对象属可选字段（`DEFAULT_KB_JSON` 补默认值机制已支持「不适用就不写」），是否需要 `schema_version` 1→2 见 §8 待裁决。
- **Strata 三层指引**：库背景属于机器资料层（`.knowledge`），不替代 Strata 的提炼结论；个人笔记若同时是人的知识，权威仍在 Strata，库内是检索副本。

## 7. 分期路线

| 期 | 内容 | 前置 | 验收 |
|---|---|---|---|
| **P0** | `background.md` 约定 + 模板包落地（纯文件约定，零代码）；现有 12 个库手工补 L1~L2 | 无 | 每个现有库有一份背景；约定写进 `.knowledge/README.md` 派生节 |
| **P1** | 前端背景编辑与完整度徽章；`_layout.json` 加 `groups[].background` | 分组方案 P1 | 建组/建库可填背景，刷新重启后保留 |
| **P2** | LLM 模块：背景补全 + 边界检查（建议-确认流） | P0、P1 | 对一个 L1 库产出可确认的背景草稿；对 12 库产出重叠报告且不写任何文件 |
| **P3** | 归组建议、模板修订建议、增量巡检 | P2 | 新库 adopt 后自动给归组建议（可拒） |

P0 不依赖本方案其他部分，也不依赖 LLM——**今天就能手工开始做**，且本身就是有价值的资产。

## 8. 待裁决（5 条）

1. **背景落盘形态**：推荐「叙述进 `background.md` + 结构化字段进 `kb.json.background`」；替代项「全进 kb.json」（长文本塞 JSON 难读难改）/「全进 md」（程序要解析自由文本）。是否同意推荐项？
2. **`kb.json` schema_version**：新增可选 `background` 对象是否升 2？（现有机制缺键补默认值，可不升；升了更明确。）
3. **LLM 凭据来源**：模块调哪个模型、走什么凭据（本地配置 / 免密钥通道），需要在实施 P2 前定。
4. **边界检查触发时机**：推荐「手动 + 新建/移动库时」，定期巡检默认关。是否接受？
5. **预设模板清单**：§3 的 8 个模板是否齐全？特别是「科研项目-其他」的口径（自筹/校内/国际合作）是否与你的实际相符。

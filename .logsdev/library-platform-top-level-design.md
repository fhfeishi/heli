# heli 上层设计 v4（实施基线）

> **状态：实施基线。** v4 按 2026-10-18 的架构建议重写后端组织方式：**一个应用、一份关系真源、五个业务模块**。
> 本版**替代** v3 的存储契约（`_layout.json` + 单库自包含）与「主归属 + 添加到其他组」模型，其余产品结论继续有效。
> 与本文冲突的旧描述一律作废；变更对照见 §0.2。

---

## 0. 一页结论

### 0.1 定位不变，组织方式变了

**以资料库为基础、以背景帮助理解、以任务驱动 Agent、以证据连接成果的本地工作台。**

主线仍是：收集 → 组织与说明 → 阅读与提取 → 研究与审查 → 形成成果，任一步可进。变的是**后端怎么承载**：
不再让每个功能各自维护文件、配置和锁，而是收敛为一个应用、一份关系真源、五个业务模块、少数明确的任务类型。

### 0.2 v3 → v4 处置

| v3 口径 | v4 | 理由 |
|---|---|---|
| 组织关系落 `<库根>/_layout.json` | **落应用库 `heli.db`** | 跨库关系、任务、引用同库查询；不再维护两套布局真源 |
| 一个库 = 自包含目录，可整体拷走 | **应用数据根统一存放**（`sources/` + `derived/` + `artifacts/`） | 单人本地研究优先；单库迁移改为导出 |
| 主归属 + 「添加到其他组」 | **普通成员关系**（多组并存，无主次） | 取消两类归属及其一致性维护；未分组 = 没有成员关系 |
| 资料四态、背景三态 | 保留 | 产品结论不变 |
| 任务 / 会话 / 执行记录 / 成果 | 保留，且**运行输入冻结**保留 | 不变 |
| 五类模板统一管理 | 保留，落到 `templates` 表 | 不建模板平台 |
| 分组/书架/卡片三视图 | 保留，共用一份数据 | 不变 |
| 旧 `kbctl` 管线 | **2026-10-18 已整包删除** | 旧库只作为 `heli import` 的只读来源 |
| 分期 A–D | 收为「第一版路径 + 后续四项」 | 第一版就有完整闭环 |

### 0.3 一句话架构

```text
前端（后续接入）
  │  统一 HTTP
  ├─ catalog     资料组织与背景
  ├─ content     文件接入、解析与原文读取
  ├─ retrieval   范围解析、检索与证据定位
  ├─ tasks       对话、Agent 执行与任务模板
  └─ artifacts   成果编辑与导出
  │
heli.db（关系/版本/状态） + 文件（原件/派生/成果）
```

模块化按**职责与依赖**判断，不按目录数量判断。首期不引入微服务、消息中间件、插件市场、通用工作流编辑器、多存储引擎适配层。

## 1. 三个产品对象

| 对象 | 解决什么 | 包含什么 |
|---|---|---|
| **资料** | 我有哪些内容、可以怎样使用 | 组、库、目录、原件、背景、提取结果 |
| **任务** | 我要用资料完成什么 | 会话、目标、范围、模板、执行状态 |
| **成果** | 这次工作留下了什么 | 报告、笔记、对比表、审查意见及引用 |

背景是组/库的属性；信息提取是一种资料加工任务；审查是一种研究任务。它们有明确实现模块，但不各自变成平台。

**首期一个任务对应一条持续会话**，支持多次执行、多个成果。不增加「项目 → 任务 → 会话组 → 会话」层级。

---

## 2. 五个模块的职责与禁止项

| 模块 | 负责 | 明确不做 |
|---|---|---|
| `catalog` | 组/库、成员关系、库内逻辑目录、名称与说明、标签与来源信息、背景、基础统计 | 不读文件内容，不做解析 |
| `content` | 导入原件、识别格式、按格式分派解析、保存派生正文与定位、提供原文/大纲读取、维护版本与状态 | 不决定分组，不做检索排序 |
| `retrieval` | 把组/库/目录/选中文档解析为实际范围、元数据过滤 + BM25、读命中附近、返回来源/版本/位置、排除下线结果 | 不生成结论，不写业务数据 |
| `tasks` | 会话、目标与范围、模板选择、运行状态与输入输出、模型调用与受控工具、取消与失败 | 不直接改组织关系，不直接写成果正文 |
| `artifacts` | 成果正文与附件、保存修订、引用、导出 Markdown/HTML | 不发起检索，不做审查判断 |

依赖方向单向：`api → tasks/artifacts → retrieval → content → catalog → storage`。`catalog` 不依赖 `content`。

## 3. 存储：一个应用数据库 + 普通文件

这是本版**最明确的一次替代**。

```text
<数据根>/
├─ heli.db          组织、背景、来源、派生索引、任务、模板、成果元数据
├─ sources/<库>/     原始资料（按库分目录，文件名不是身份）
├─ derived/<sha前2>/ 解析正文（可重建）
├─ artifacts/<id>/   成果正文、附件、导出文件
└─ temp/            可清理
```

约定：

- **数据库负责身份、关系、版本、状态**；文件负责原件与大内容。
- **文件名/目录名不是身份**：改名、归组、调目录只改元数据。
- 全文索引（FTS5）放在同一个 `heli.db`，逻辑上属可重建数据，可随时 `reindex`。
- JSON / Markdown 导出用于查看、交换、备份，**不做第二套同步编辑源**。
- 数据根由 `HELI_DATA` 或 `--data` 指定，默认 `<项目根>/heli-data`；不与旧 `.knowledge` 混放。

**这个选择牺牲了「拷走一个库目录就恢复单库」**：单库迁移改为「导出包（元数据 + 原件 + 成果）」。换取的是跨库组织、任务与引用关系只有一处真源。

---

## 4. 分组：普通成员关系，没有主归属

- 组可以含子组与库（树深上限 3），**不要求只有叶子组能放库**。
- 一个库可以同时属于多个组，**没有「主要归属」与「镜像」之分**：加组只是加一条成员关系；移组是移除旧关系 + 添加新关系。
- **未分组 = 没有成员关系**，由查询算出，不存「未分组」字段。
- 每个组内维护 `order_index`；同一库在不同组可以有不同位置。
- 组背景、库背景都是自述（§5）；组背景**不自动写入**库背景。

界面上「移到其他组」与「同时放入另一组」是两种不同意图，文案必须分开，不能都叫「移动」。

---

## 5. 背景：允许模糊，三件事并存

背景回答：为什么建、收什么、打算怎么用、有哪些已知缺口。

| 表达 | 含义 | 并存规则 |
|---|---|---|
| 已保存版本 | 用户确认过的正文（带版本） | 可与未采纳建议并存 |
| 待采纳建议 | AI 生成、未采纳的 diff（含依据） | 与已保存版并存，逐段采纳 |
| 待澄清项 | 缺依据、含糊或与资料冲突的条目 | 与任何状态并存 |

- 建库只要求名称；写「一些农业 AI 项目材料」就能用。
- **不把「填满」当「可信」**；不强制边界互斥，重叠只做提示且必须给依据。
- 无模型时手工背景可用；AI 入口隐藏并注明未配置。

## 6. 接入与解析：原件、派生、结果分开

| 载体 | 首期能力 | 证据定位 |
|---|---|---|
| 文本 / Markdown / JSON / CSV | **直读**，进全文索引 | 字符区间 |
| PDF | **只登记**（当前无可靠解析库），标 `needs_parser` | 无 |
| Office / 图片 / 音视频 / 代码 / 数据集 | **只登记**，可下载 | 无 |

- 不能解析的资料仍是**合法资料**：状态 `registered`，可下载、可归类，**不产生乱码正文**。
- 解析按显式分派函数（扩展名 → 解析器），首期不做插件框架。
- `content` 只写 `sources / versions / derived`，删除只标 `archived_at`，不物理删原件。

---

## 7. 检索与证据

```text
resolve_scope(selection)   # 组/库/目录/选中文档 → 实际 source 集合
search(scope, query)       # 元数据过滤 → BM25 → 命中列表
read(source_id, version)   # 打开当时使用的那一版正文
```

- Agent 与普通搜索共用这三个函数，不各写一套。
- 结果带 `source_id / version_id / 位置 / 摘录`；**只有逐字匹配才给字符区间**。
- 已下线（`archived_at`）的来源不进入新结果；历史成果仍能按引用打开（§9）。
- 组范围按**库**去重；同内容不同来源（`sha256` 相同）折叠展示，但**保留各自出处**，不自动算独立佐证。

## 8. 任务与运行

### 8.1 对象关系

```text
task 1 ── n message        （一条持续会话）
task 1 ── n run            （每次实际执行）
run  1 ── n artifact       （草稿/成果）
```

### 8.2 运行状态机

```text
queued → running → done | failed | cancelled
                  └─ cancelling（已请求取消，未落地）
启动时把上次未结束的 run 标为 interrupted
```

- 状态由后端持久化，前端只订阅；**不用本地计时假装进度**。
- 异常退出后不静默重跑（不重复付费调用），标 `interrupted` 让用户重试。
- 普通读写同步返回；解析、批量提取、研究、导出进后台执行器（首期进程内串行）。

### 8.3 运行输入冻结

创建 run 时由**后端**解析并写入 `runs.input_json`：

| 冻结项 | 内容 |
|---|---|
| `scope` | 选择的原始表达（组/库/目录/文档） |
| `resolved` | 实际库 id、source id 列表 |
| `versions` | 每个来源实际读取的 `version_id` / `sha256` |
| `background` | 参与库的背景快照哈希 |
| `template` | 模板 id + 版本 |
| `started_at` | 开始时间 |

运行期间新增或更新的资料**不自动纳入**；重跑重新解析范围，生成新的 run，成果不覆盖旧版。

### 8.4 四类任务处理函数（不是四个 Agent）

| 类型 | 做法 |
|---|---|
| `background` | 一次结构化生成（补全 / 归组建议） |
| `extract` | 逐文档执行并汇总（按字段） |
| `research` | 有限循环：搜索 → 阅读 → 生成 |
| `review` | 确定性检查 + 模型分析 |

只有需要动态选步骤的 `research` 才走 Agent 循环。四者共用模型客户端、运行记录、证据结构。

**未配置模型时**：`research` 退化为「证据包」——把范围内命中的原文摘录与定位整理成草稿成果，并在正文首行标注「未接模型，仅检索结果」。不假装生成了结论。

## 9. 成果

- 成果正文以 **Markdown** 为工作格式（表格、图片、引用都是 Markdown 能表达的）。
- 每次保存生成一条**修订**，可回到上一版；不覆盖人工编辑。
- 引用记录 `source_id + version_id + 位置 + 摘录`；来源下线后引用仍可打开当时版本，缺文件则标「来源不可用」。
- 导出：Markdown 必做；HTML 次之；DOCX 是输出能力，不作为内部存储格式。

---

## 10. 模板：轻量，五类分别校验

| 类型 | 内容 |
|---|---|
| 背景 | 引导字段 |
| 提取 | 字段定义、记录粒度、缺失处理 |
| 研究 | 任务要求与步骤提示 |
| 报告 | 大纲、必需内容、呈现要求 |
| 审查 | 检查项、适用依据、严重度 |

共用 `templates(id, kind, name, version, body_json)`；不同类型各自校验字段。**不建模板平台**。
一个库可关联多份提取方案，用关联表表达，不增加 `target_task2/3`。
上传样本生成的是**待确认模板**（识别结构，不承诺复刻复杂排版）。

---

## 11. Agent 约束

- Agent 只拿本次任务需要的工具：搜索选定资料、阅读指定来源、读库背景、提交候选结果/成果草稿。
- **背景与导入内容是上下文，不能改变权限**；改正式背景、覆盖人工成果要经业务校验与用户确认。
- 工具调用记录展示**做了什么**（参数、结果、耗时），不暴露模型内部推理。
- **本地保存 ≠ 本地推理**：设置里显示实际模型通道；外部调用遵循配置范围，不带无关原文与凭据。

## 12. 源码组织

```text
heli-src/             后端源码根（不再套一层 Python 包，模块同级导入）
├─ app.py            启动与组件装配
├─ routes.py         请求解析、参数校验、响应形状
├─ catalog.py        组/库/成员关系/背景
├─ content.py        导入、读取、按格式解析
├─ retrieval.py      范围、检索、证据
├─ tasks.py          运行管理与四类任务处理
├─ artifacts.py      成果保存与导出
├─ storage.py        连接、事务、文件写入
├─ models.py         跨模块数据结构
├─ config.py         唯一配置入口
├─ pipeline.py       批量处理审计（写 datapipe/runs）
└─ cli.py            维护入口（同一批业务函数）

tests/                端到端检查，与 heli-src 同级

datapipe/             数据转换审计
└─ runs/             一次批量处理一份 JSON：输入、规则、计数、跳过原因、错误
```

前端（`heli-web/src`，沿用既有设计令牌）：

```text
heli-web/src/
├─ app/         自研路由（URL 即 UI 状态）
├─ model/       v4 API 客户端 + 工作区状态（只放多视图共享的列表）
├─ views/       资料库总览 / 库内 / 研究任务 / 成果 / 设置
├─ components/  ui.tsx、Icons（复用令牌，不重画一套）
└─ styles/      令牌与全局样式
```

旧组件（`store.tsx`、`data/mock.ts`、旧 `components/` 等）**已删除**，WSL 清理完成；
不要再从历史提交里恢复它们。

约束（比目录重要）：

1. `routes` 不写业务 SQL、不直接改文件；
2. 业务模块不依赖 HTTP 请求对象；
3. 不跨模块调 `_private`；
4. 查询归对应模块所有，不给每张表建 Repository；
5. 模块过大或职责分裂时再拆目录；
6. **不保留两套生产写路径**——旧 `kbctl` 已整包删除，旧库只作为导入来源；
7. **批量转换必须留审计记录**——`import` / `reparse` / `reindex` 写 `datapipe/runs/`，
   记录输入、规则、计数与跳过原因；记录是旁路，不参与业务判断。

## 13. 第一版交付范围与验收

**路径**：建库与分组 → 导入资料 → 预览与检索 → 选范围对话 → 核对引用 → 保存并导出成果。

**已实现（2026-10-18，见 `tests/test_app_http.py`）**

| 能力 | 接口 |
|---|---|
| 建库 / 改名 / 归档 | `POST/PATCH/DELETE /api/libraries` |
| 建组 / 改名 / 删除 / 成员 | `POST/PATCH/DELETE /api/groups`、`PUT /api/groups/<id>/members` |
| 导入原件（文本类解析进索引） | `POST /api/libraries/<id>/sources` |
| 读原文 / 读正文 | `GET /api/sources/<id>/original`、`/text` |
| 范围检索 + 证据 | `GET /api/search?q=&scope=...` |
| 会话与任务 | `POST /api/tasks`、`POST /api/tasks/<id>/messages` |
| 运行（含证据包） | `POST /api/tasks/<id>/runs`、`GET /api/runs/<id>`、`/cancel` |
| 成果保存 / 修订 / 导出 | `POST /api/artifacts`、`PATCH /api/artifacts/<id>`、`GET /api/artifacts/<id>/export.md` |
| 前端四视图 | `/knowledge` 组与库、`/knowledge/<id>` 资料与正文、`/research` 任务、`/artifacts` 成果、`/settings` |

**验收断言（全部有测试）**

1. 重启后资料、分组、成果仍在；
2. 归档的库/来源不再进入新检索与答案；
3. 引用能打开当时使用的版本；文件缺失时标「来源不可用」；
4. 运行失败/取消不冒充完成，不覆盖人工成果；
5. 错误写入不清空现有数据（事务 + 原件先落盘后发布）；
6. 不可解析格式不产生乱码正文；
7. 同一个库加入两个组后，两个组都能看到；移除关系不影响原件。

**前端验收（2026-10-18）**：`tsc --noEmit` 与 `vite build` 通过；1440×900 实测资料库总览、库内检索与命中高亮
（「命中位置 2」）、任务运行记录（起止时间 / 命中 3）、成果页引用与导出按钮。旧 mock 组件不再被引用。

**未做（下一轮）**：PDF/Office/音视频解析、背景 AI 模块、报告模板上传识别、审查规则引擎、DOCX 导出。
书架/卡片三视图尚未接入（当前是列表 + 卡片；书架视图留待与拖拽一起做）。

## 14. 旧系统与迁移

- **旧 `kbctl` 已删除**：旧库不再有独立服务与 CLI；接入统一走 `python heli-src/cli.py import`。
- 旧 `.knowledge` 目录**不移动、不改写**；`_layout.json` 不再创建。
- 一次性导入：`python -m heli import --from <旧库根> [--library <slug>]`，逐个复制 `source/` 原文，按新库登记；
  旧库 `kb.json` 的 `name`/`description` 作为初始元数据。导入只读源端。
- 旧库的 `parsed/`、`target/`、`vectordb/` **不导入**：新架构按需重新解析，避免把旧结构当新契约。

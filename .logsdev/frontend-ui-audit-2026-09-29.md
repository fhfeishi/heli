# heli 前端 UI 审核（2026-09-29）

审核人：智能设计助手（UiDesigner 流程）。
范围：`heli-web/src` 当前实现（15,653 行 / 36 个组件），`npm run dev` + 真实后端（`langchain_docs` 1,423 篇 + 自然科学基金系列共 12 库）逐页截图走查，视口 1440×900 与 1440×2400 两档，覆盖全部 10 类路由页面；代码侧核对全部组件引用关系与关键实现。

---

## 0. 总评

1. **骨架已经立住**：U1 四入口导航、路由化 UI 状态、U6 面板并排/浮层模式都已落地，S1 的核心链路（目录 → 列表 → 阅读 → 刷新恢复）真实可用。
2. **研究侧明显好于资料侧**：会话页（引用卡、操作条、token 统计、composer 配置）和成果页是全站观感最好的两页；资料库工作区则被顶部 chrome、失衡的三栏和工程化文案拖累。
3. **最大的问题不是"不好看"，而是"不干净"**：库页顶部约 230px 的三层导航 chrome 在每个页面重复；书架/卡片体系（约 3,250 行）带着 mock 假数据悬在真实库旁边；设置页把裁决编号（U1/U2）、Vite 代理、CLI 命令直接写在界面上。

## 1. 美观问题（按严重度）

### P1 — 直接影响使用

**1.1 库页顶部三层 chrome，约 230px，且在阅读页照常渲染**
- 证据：`KnowledgeView.tsx` L332–348。构成：大标题「资料库」+ 副标题（与 `/knowledge` 列表页标题完全重复）→ 12 个库的标签云按钮（`flex-wrap` 两行）→「库概览 / 信息提取 / 处理记录」三个按钮被 `flex-wrap` 散落成左/中/右三段 →「资料库 / 书架整理」切换条 → 库名 + 统计 + 重命名按钮。
- 后果：1440×900 下三栏内容区只剩约 45% 视口高；读一篇文档时以上全部在场（阅读页与列表页共用同一渲染分支）。
- 三按钮散落是 flex-wrap 的副作用：三个等权按钮被推到行首/行中/行尾，视觉上像断线的三个孤岛。

**1.2 阅读区可读性不足**
- 正文列宽无上限（`article` 占 `minmax(0,1fr)`，L417）：在 1440 宽下长行超过 1,100px，远超舒适阅读宽度（65–75 字符）。
- 章节导航用原生 `<select>` 占满整行（L437），观感是表单不是阅读器；「完整章节 · N 字符 · 已定位到检索命中（第 N 字符）」这类实现细节以正文同级字号平铺（L443）。
- 字号 14px / 行高 1.7 的正文放在大片留白中间，字号与留白比例失衡。

**1.3 三栏比例失衡 190 / 210 / flex（L362）**
- 文档列表栏仅 210px：条目两行制（标题 + 路径）在这个宽度下标题必然截断（截图中「The open agent engi…」），路径小字与标题高度重复。
- 目录树 190px 塞下 96 个章节的深缩进，可读性勉强。
- 未选中文档时右栏是 65% 宽的白板空态（L418「选择一篇文档阅读」），页面重心感尽失。

### P2 — 不一致与不专业

**1.4 两套数据并存**：列表视图连真实库（`/api`），切到「书架整理」却是 mock 假库（固态电池产业研究等，`mock.ts` L260+）。用户在同一个库里切换视图，看到的是两个世界的资料。

**1.5 工程语言外露（逐条定位）**
| 位置 | 文案 |
|---|---|
| `SettingsView.tsx` L16 | 「Vite 开发代理到此地址；桌面端改为直连」 |
| L21 | 「落盘命名以 .knowledge/README.md 的术语表为准」 |
| L31 | 「U2：向量检索为可选增强，单独排期」 |
| L36 | 「U1：不占一级导航。…」 |
| `ExtractView.tsx` L75 | 「自动提取运行尚未接通；原文检索使用 BM25 全文索引」 |
| `JobsView.tsx` L95 | 「已导入的解析和提取文件不代表本应用执行过这些任务，外部处理历史尚未提供」 |
| `KnowledgeView.tsx` L394 | 检索框下方平铺 CLI 命令 `python -m kbctl --root .knowledge --kb … v2-manage search-index` |
| `KbWorkspace.tsx` L161 | 「本地仅 · 19:41:27」带时间戳 |

裁决编号、内部文档名、命令行、构建工具名都是写给开发者的，不是写给用户的。

**1.6 导航模式不统一**：全站只有「处理记录」页有面包屑；返回链接措辞各异（「返回目录与原文」「返回资料 处理记录」「返回文档列表」）；extract 页又没有库 chrome，像孤页。

**1.7 「新建研究」按钮双份**：左栏顶部（`SidePanel` research tab header action）与主区头部（`ResearchHomeView` L22）各一个，同屏同优先级。

### P3 — 精修项

- 成果页：两张卡片各一个大号紫色主按钮「打开预览」并排重复；筛选 chips（全部 6 / 已完成 3 / …）与卡片状态徽章重复表达同一信息。
- 研究首页：每张模板卡片双按钮（「开始这个任务」「查看详情」），主 CTA 权重被稀释。
- IconRail 纯图标无文字标签，可发现性依赖猜测。
- 空态缺乏引导（右栏白板、模板区空态文案弱）。

## 3. 整改建议（按投入产出排序）

**第一批：减法（改动最小、观感收益最大）**
1. 库 chrome 收缩为一行：`库名 · 统计 · [信息提取] [处理记录] [库概览]`；原 230px → 约 60px。删除大标题重复、标签云、三按钮散落行、「资料库/书架整理」切换条。
2. 阅读正文：列宽 `max-w-[760px]` 居中、正文字号 14→15px、章节选择器改为顶部「章节 ▾」胶囊 + 上一章/下一章；元信息（字符数、字符定位）降为微字号灰色单行。
3. 三栏改 `240 / 340 / flex`；列表条目去掉路径行（改为 hover 显示或仅标题）；空态改为居中窄空态 + 最近阅读 3 条。

**第二批：去工程语言 + 导航统一**
4. 设置页 hint 全部重写为用户语言（如「向量检索：规划中，当前使用全文检索」）；内部文档名与构建工具名移入文档链接。
5. extract / jobs 页横幅收敛为一句状态说明 +「了解处理链路」帮助链接；CLI 命令折叠成「复制索引命令」按钮。
6. 统一面包屑组件：`资料库 / <库名> / [处理记录 | 信息提取 | <文档名>]`，四个页面共用。
7. 「新建研究」只留主区一个。

**第三批：结构性（按 U3 落实）**
8. 书架体系 3,250 行按 2.2 处置（移出库工作区 → 接真实库或冻结）。
9. 删除 2 个 stub 文件。

## 4. 应当保持的部分（不要在整改中误伤）

- **会话页**是全站质量基准：引用卡（相关度 + 来源标签 + 摘要）、复制/导出/重新生成操作条、token 统计行、composer 配置 chips——资料侧改版时应向它对齐。
- 交互判断正确且应保留：检索范围显式披露（「全文检索 1,423 篇」）、空结果不静默扩大（「扩大到全库」是显式动作）、索引未就绪独立提示且不阻断阅读、错误横幅带下一步。
- 「从当前章节移除 / 加入当前章节」的措辞区分符合"三种树动词分离"的方案要求。

## 2026-09-27 · 知识库落盘命名与权威源

**决定**

1. 落盘命名收敛为单一术语表：`source/ / parsed/ / vectordb/<engine>/ / datadb/kb.db / kb.json / manifest.jsonl / nav.json / links.jsonl / _registry.json / _scratch/ / _status.json`。废止 `raw/`、`vector/`、库根 `kb.db`、`index.json`、`structure/` 目录。前端 `KbStorage` 的 `raw` / `vector` 字段同步改名为 `source` / `vectordb`，`db` 指向 `datadb/kb.db`。
2. `langchain_docs` 的权威源层取 `archive/source`（**1438 个文件，含 13 份 `llms.txt` + `_manifest.json` + `README.md`**），不是 `source_demo/source`（1423 个）。导航原始件按规范留在 `source/` 原位，用 `kind=nav_source` / `value_class=nav_only` 过滤。

**适用范围**：`.knowledge/` 下所有库、`heli-src/kbctl/`、前端 `KbStorage`。

**理由与替代关系**

- 命名：原有四套命名（约定文档 / 前端 / 磁盘 / 04 号文档）并存，后端当时一行未写，是成本最低的一次一致性修复。
- 权威源：实测 `archive/source` 与 `source_demo/source` 在 1423 篇重叠文档上**逐文件 sha256 完全一致**，差集恰为 15 个导航原始件 + 1438 个 ADS。规范 §2.2 要求导航原始件留在源层（移出即修改原始快照），故取超集。`source_demo/structure/` 降级进 `_scratch/` 保留，作为后续对账参考。

**实施规格**：`.logsdev/archive/knowledge_persistence/knowledge-persistence-optimization.md`
**交付报告**：`.logsdev/archive/knowledge_persistence/phase0-3-delivery.md`

## 2026-09-27 · 第二轮审核后的发布与保留边界

**依据与范围**：用户在审核复核后要求继续实施，落实存储契约补充；适用于新格式设计与后续实现，不授权现有库迁移或清理。保留此前落盘命名与来源选择记录；旧数据盘点有差异时另行核对，不能静默替换权威源。

**决定**

1. 以 SQLite 为当前发布指针及成员关系的唯一权威，_engine.json 仅为摘要。取代旧 README 的先删后写要求；旧 CLI 仍需改造，不声称已支持此协议。
2. 一期实现方向为同模型集合内保存不可变分片、SQL 固定发布成员；换模型或不可变索引配置建立新实例。与全量 collection 快照的比较、选择依据见规格 §2.1。Windows 小规模真实 Chroma 探针已通过，目标 WSL、故障与并发准入仍未通过；选择是实现方向，不是性能或可靠性认证，验证推翻假设时回到方案比较。
3. 一期显式改名保留来源 ID，未知路径按新来源处理；不引入自动移动识别和人工待确认队列。完整扫描的下线与访问失败严格区分。
4. 将旧向量回收与历史证据保留分开：安全点可回收无依赖旧向量，一期不自动删除历史原文、解析、SQL 分片和引用证据。永久删除及回收站期限仍待产品选择。
5. 旧库接管以小库端到端验收、旧库只读盘点、独立副本演练为前置条件，不靠日期或旧文件数量直接准入。

协议和最小关系模型唯一维护在 [修订规格](archive/knowledge_persistence/knowledge-persistence-optimization.md)；证据与限制见 [探针记录](archive/knowledge_persistence/knowledge-persistence-review.md#publication-probe)。


## 2026-09-27 · 按精简要求收敛模型

依据：用户要求“精简的、高效的设计”，授权本轮方案优化。采用 sources、versions、chunks、kb_state、jobs 五张核心表，导航/链接只保存当前关系；以变化来源的版本指针与集合指针的一次 SQL 提交取代 publications 及全库成员快照。引用保存当时证据，历史原文与处理版本保留。

替代范围：前节第 1、2 条中的独立 publication 实体及成员快照，改为当前来源版本与集合权威；同模型不可变分片、换模型新集合方向不变。先前命名清单中的 manifest/nav/links/_registry/_status/_engine 改为可选导出，非必需同步状态；不删除现有文件。版本化处理合并独立 content/parse/chunk_set 表，一期不做通用 job_artifacts 或历史读者依赖图。

单写任务队列加一把存储操作互斥锁取代多层读写门，远程处理在锁外；GC 只在无未完成更新任务的安全点处理旧向量。来源选择、旧库接管和历史证据保留边界继续有效。五表方案不提供任意历史整库视图；此能力未列为当前需求。

本决定是设计方向；未修改生产 schema 或运行数据。查询过滤规模、锁等待及恢复须由 [规格 §6](archive/knowledge_persistence/knowledge-persistence-optimization.md) 验收；已有探针不构成该方案实现通过。

## 2026-09-28 · 稳定章节与真实库资料管理

依据用户继续实施及整理真实库的指令，保留五表底座，新增 sections 与 section_documents；章节为稳定 ID 的树，文档允许多归属。扫描导航与人工组织分开，结构 JSON 只导出，不引入第二编辑源。相较物理目录唯一结构和 JSON 权威，这一选择复用 SQLite 约束且支持章节移动、空章节和多归属。

真实库先落地资料组织与冻结原文阅读，向量索引状态独立披露。原文不改，旧导出转存库内回退目录；这替代先前“仅设计、不写原库”的范围，未授权永久删除资料。同步本地接口暂用全程可重入库锁，接受长构建期间同库读操作返回忙；先前短锁／写队列仍是未实现的优化方向。

当前原则及结果统一维护在 [.knowledge/README.md](../.knowledge/README.md)，不再依赖旧章节编号；验证见 [管理交付](archive/knowledge_persistence/management-delivery.md)。

## 2026-09-28 · 前端顶层设计的授权范围与方案载体

**依据与范围**：用户 2026-09-28 要求为 heli 前端输出顶层设计方案，明确可以推翻历史结构与技术选型（含不限于 React + Tailwind v4），但须给出对比与理由，并要求参考成熟开源实践。适用于 heli 前端的架构与选型讨论，不授权实施，也不改动知识库落盘与结构决定。

**决定**

1. 前端方案可提出替代结构、技术选型与目录划分，但每条必须给出被否方案与理由；技术栈不限于当前草稿。
2. 方案的信息归属按 `.agents/DOCUMENTS.md`：候选与论证只维护在 `.logsdev/frontend-top-level-design.md`；工作安排与待裁决项摘要进 `PROJECTION.md`；执行状态进 `INTERACTION.md`；**只有形成已确定决定后才写入本文件**，且不搬入分析过程。
3. 方案在用户批准前不是已确认要求，不启动实施。批准后在本文件写入决定条目、适用范围与替代关系，方案正文转为实施规格。

**理由与替代关系**

- 载体归属：替代「把方案全文写进 DECISIONS」的写法。DECISIONS 只记已确定决定，未批准的方案写入会使该文件同时承担"已定"和"待定"两种状态，后续无法区分哪些条目已生效。分析过程留在方案正文，三个载体只保留摘要与链接，避免同一事实多处维护。
- 位置取 `.logsdev/` 顶层而非 `.logsdev/archive/`：后者被其自身 `.gitignore`（内容为 `*`）排除，不进版本库；顶层文件受跟踪。这与既有 `knowledge-v2-redesign-handoff.md` 的放置一致。

**适用范围**：`.logsdev/` 下的前端方案、其工作安排与执行记录。知识库落盘命名、权威源、章节与来源语义仍按此前决定执行，不受本条影响。

**后续**：本条第 3 点的"批准前不启动实施"已于同日完成——方案经用户裁决通过，决定条目见下一条 [2026-09-28 · 前端顶层设计已批准](#2026-09-28--前端顶层设计已批准产品结论与九项裁决)。

## 2026-09-28 · 前端顶层设计已批准：产品结论与九项裁决

**依据与范围**：用户 2026-09-28 批准前端顶层设计方案 v2（[正文](frontend-top-level-design.md)），并要求 U1–U9 按方案倾向执行。适用于 heli 前端（`heli-web/`）的信息架构、交互规则与实施顺序；不改动知识库落盘命名、章节与来源语义、锁与并发边界（仍按此前决定与 [.knowledge/README.md](../.knowledge/README.md)）。工程选型不在此列。

**决定**

1. 方案 v2 批准，正文转为实施规格。产品结论（§1–8）与实施顺序（§16）构成当前实施范围：先 **S1 读懂资料**，再 **S2 加工资料**、**S3 完成研究**；工程地基（S0）只在被某场景需要时做，不单独铺开。
2. 九项裁决（逐条与落地含义见正文 §17.1）：
   - **U1** 一级导航为**资料库 / 研究任务 / 成果 / 设置**四项；对话不占一级入口，并入研究任务；`skills` 归入模板高级配置；`/knowledge` 等前缀**现在定**。
   - **U2** 本轮检索范围 = **目录 + 原文 + 全文检索（BM25 优先）**；向量检索为可选增强、单独排期、不阻塞前端。
   - **U3** 书架**降级**为「多库浏览」的可选视图；库内一律列表/表格；不进本轮验收路径，代码保留但不优先投入。
   - **U4** S2 以后端提供 `target-schema.json` 样例与提取接口为前置；此前只做契约 + MSW mock + 界面骨架并标注未接后端，**接真实接口才计入验收**。
   - **U5** 组织视图（分组/顺序/镜像）**落盘**，作为独立于 `sections` 的视图数据；后端提供前存 localStorage 并标注「本地仅」。
   - **U6** 右侧面板**按模块区分**：资料库并排常驻、对话/研究任务浮层、窄屏允许切换主视图。
   - **U7** 「停止」走**后端真实取消**；界面区分「已发出」与「已确认」，不得点了就算停。
   - **U8** 成果**显式保存**；未保存时点击引用先提示保存/放弃，不静默替换。
   - **U9** 提取方案显式声明 `record_scope`，**默认 `document`**，允许 `segment` / `entity`；结果表首列必须显示「本行代表什么」。
3. 工程选型（路由库、状态库、目录粒度与搬迁时机、测试工具与用例取舍、虚拟化与 Worker 引入时机、DTO/VM 分层边界、构建与 lint 配置、图标/拖拽/Markdown 库、Tauri 集成方式）**由实现者按证据决定**，不再提交用户裁决。

**理由与替代关系**

- **U1 对话并入研究任务**：替代「保留 chat 为独立一级入口」。会话是任务的一部分，独立入口会让"这次讨论属于哪个任务"失去归属；代价是默认首页由空对话变为任务列表，需迁移现有 `nav="chat"` 默认值与首次进入引导。
- **U2 检索范围**：替代「把 `.knowledge/README.md` §6/§8 的 BGE-M3 + Chroma 当作本轮需求」，也替代「把 bm25 当作已实现的替换方案」。补充证据：真实库 active 索引 0、向量文件 0，**且 BM25/FTS5 同样未实现**——两条路都仍需后端工作量。前端只依赖「检索通道契约」（范围 + 查询 → 命中 + 字符偏移），故本条裁决不改变前端设计，只锁定后端本轮范围。
- **U3 书架降级**：替代「书架作为知识库主视图」。书架解决的是多库摆放，本轮核心是进入库后读懂与加工资料；列表/表格更适合筛选、比较与批量。降级而非删除，保留 `/knowledge` 库列表的视图切换能力。
- **U4 mock 不算完成**：替代「先做完整前端再等后端」。避免重演既有缺陷 P9（未接后端的动作伪装成功）；契约与 mock 先行可以并行，但验收必须落在真实接口上。
- **U5 落盘**：替代「组织视图只存 localStorage」。分组与顺序是用户资产，只存本地会在换设备/清缓存后丢失，且无法与后端 `sections` 区分责任；落盘为独立视图数据既不污染 `sections` 语义，也保留"未提供前标本地仅"的过渡口径。
- **U6 按模块区分**：替代「统一布局」。现有 `App.tsx` 是"知识库页不渲染 Inspector"，与裁决相反——知识库恰是最需要并排面板的模块，故以本条为准改造。
- **U7 真实取消**：替代「前端关闭流即视为停止」。不真实取消会继续消耗 token，界面上"点了就停"是假反馈。
- **U8 显式保存**：替代「自动保存」。成果是会被引用与继续编辑的产物，静默替换等于让用户丢失未确认的修改；显式保存 + 冲突提示成本更低且可预期。
- **U9 默认 document**：替代「不声明粒度（隐含一篇一行）」。一篇文档可能含多个实验或实体，隐含假设会让结果表被误读；显式声明并把粒度显示出来是最小成本的正确做法。

**适用范围**：`heli-web/` 前端的架构与实现；后续变更先改方案正文，再同步本文件、PROJECTION 与 INTERACTION。

**实施规格**：[.logsdev/frontend-top-level-design.md](frontend-top-level-design.md)（已裁决版）；裁决后快照 `archive/frontend-top-level-design/frontend-top-level-design-v3-2026-09-28.md`（`archive/` 不入版本库）。
